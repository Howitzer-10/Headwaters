## Part 2: Ticket

### HDW-201 · Shared daemon, internal API, port handling
**Model** Sonnet · **Effort** High · **Depends** 117, 002 · **Class** Core · **Refs** v3.4 §B3, v3.1 §C3
**Build:**
- `headwaters daemon` process: single-instance lock, owns the Router, catalog refresh and keep-warm.
- An internal JSON API on 127.0.0.1 (token-authenticated via a per-user secret file) plus a **streamable HTTP MCP endpoint** for hosts that support it.
- Port selection: check the Hyper-V/WSL excluded ranges (`netsh int ipv4 show excludedportrange protocol=tcp`), fall back to the next free port, and write the chosen ports to a state file other components read.
- Health endpoint; graceful shutdown; `headwaters start|stop` commands.
- (FU-124-1, triage) `.importlinter` (HDW-124) lets only `headwaters.gateway` import `fastapi`/`starlette` and only `headwaters.mcp` import `mcp`. The repo layout puts the daemon and its internal HTTP API under `headwaters/mcp/`, and the daemon shares one process with the gateway (D7). Before writing code, settle which package owns the HTTP server and change the contract in this ticket if needed; record it in ASSUMPTIONS, or in DECISIONS if a package boundary moves. When the first web-framework import lands, show the contracts still bite.
**Accept when:** two clients share one daemon; the excluded-range parser is tested with sample output; the daemon refuses non-loopback binds; `lint-imports` keeps every contract with the real daemon code in place, and a throwaway `import starlette` from `headwaters.core` fails it.

### Excerpt: v3.1 addendum §C3

#### C3. Networking and ports
- Bind to `127.0.0.1` only (avoids a Windows Firewall prompt and stays private).
- Before binding, check the Hyper-V/WSL excluded port ranges (`netsh int ipv4 show excludedportrange protocol=tcp`). Fall back to the next free port and write it back into the IDE snippets.
- Default ports 4000 (gateway) and 4001 (dashboard) are configurable.


### Excerpt: v3.4 addendum §B3

#### B3. MCP spec feature map (verify each against the current spec version and per-host support)
| Feature | Use |
| --- | --- |
| Structured output / outputSchema | All tools |
| Tool annotations | readOnly / destructive / idempotent hints so hosts can auto-approve safe tools |
| Progress notifications | Cold loads, drafting, escalation |
| Async tasks (spec Tasks primitive if available; else job_id pattern) | Long runs, Fusion |
| Elicitation | Spend confirmation, scope loosening (user-only) |
| Resources (+ subscriptions) | `headwaters://status`, `headwaters://savings`, `headwaters://result/<id>`, `headwaters://handoff/<id>` |
| Prompts | `/headwaters-local`, `/headwaters-free`, `/headwaters-auto`, `/headwaters-duck`, `/headwaters-handoff` |
| Roots | Workspace boundary for path reads |
| Sampling | Optional: let the host model serve as a tier when the host allows it (never in local scope) |
| Transports | stdio (default) + streamable HTTP (shared daemon so multiple IDEs reuse one warm GPU model) |

**Shared daemon:** stdio MCP processes are thin shims to one Headwaters daemon, so three IDEs open at once don't each spawn a router or compete for VRAM.
