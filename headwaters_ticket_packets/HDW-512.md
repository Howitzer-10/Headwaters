## Part 2: Ticket

### HDW-512 · Tool capability truth, live overrides, an honest pull hint, and the answer footer

**Depends** HDW-511 (owns the composition-honest `local_unavailable` error text; this ticket
does not duplicate it) · **Model** Sonnet · **Effort** High

### The defect

Cline (an MCP/OpenAI-compatible host) dogfooding Headwaters through the gateway showed a tool
call in its chat as a raw fenced JSON block:

```
{"name": "skills", "arguments": {"skill": "test"}}
```

That is a tool call delivered in the **content** channel instead of the structured `tool_calls`
channel. Measured facts (already reproduced by the coordinator; do not redo the measurement):

1. The router chose `qwen2.5-coder:14b` for that request (`decisions` id 6, rung `best_effort`,
   score 36.0 vs floor 74.0, "offloaded to system RAM: -30.0 points").
2. `POST 127.0.0.1:11434/api/chat` with a `tools` array and "Call the headwaters_status tool
   now": `qwen2.5-coder:14b` returns `tool_calls=null` and
   `content='{"name": "headwaters_status", "arguments": {}}'` (`done_reason` `stop`). Through
   the gateway the output is identical, so this is **not** a gateway conversion bug.
3. `qwen3:8b`, `gpt-oss:20b`, `qwen3-coder:30b` and `devstral-small-2:24b` all return a real
   structured `tool_calls` entry with empty content on the same probe. `GET/POST /api/show`
   still advertises `capabilities ['completion','tools','insert']` for
   `qwen2.5-coder:14b` — advertisement and behaviour disagree.
4. `headwaters/core/state_models.py` (`upsert_model`) is the only writer of `models.tools_ok`,
   and the value comes from the provider's **advertised** capability (`catalog/sources.py` →
   `catalog/merge.py`), never from observed behaviour.
5. `ModelsRules.overrides` (`headwaters/core/rules.py`) is validated and applied once at
   discovery time (`catalog/merge.py:_apply_override`), but **the routing path never reads it**:
   a rules edit only reaches a decision after a full `models refresh`, and score overrides are
   only visible through the persisted `scores.override` column. A user cannot correct a wrong
   `tools_ok`, `json_ok`, `ctx`, tier or score at the moment of routing.
6. The `pull_model` suggestion recommends the model it just chose:
   `headwaters pick --tools --tokens 15000 --scope local` → chosen `qwen2.5-coder:14b` **and**
   `suggestions[0] = {code: pull_model, text: 'Pull a larger local model that fits your GPU:
   pull qwen2.5-coder:14b.'}`. The hint comes from
   `headwaters/core/router_prep.py:pull_hint`, which reads the catalog GPU profile and never
   checks what is installed.
7. The coordinator's temporary workaround (hand-setting `tools_ok = 0` in
   `%LOCALAPPDATA%\Headwaters\headwaters.db`) is **superseded** by this ticket: models refresh
   restores the advertised value, so the fix must be behavioural and refresh-proof.

### Scope: four slices, all required

#### Slice A — verify tool capability behaviourally

Add a bounded verification that asks a model to call a trivial synthetic tool and records
`tools_ok` from whether a **structured** `tool_calls` entry came back (empty content, tool name
matching the offered tool). A model that returns the call as text ends up `tools_ok = 0` and the
observation is recorded.

Requirements:
- never runs on a request path (no added latency on the hot path);
- respects the local-only/private/airplane locks (no outbound call when a lock forbids it);
- bounded by the existing executor timeouts, plus a per-run model cap;
- idempotent (same observation repeated = one row) and skips a model verified recently;
- a model that could not be verified never becomes `tools_ok = 1`.

**Decision (documented here, implemented in code):** verification runs on an **explicit
command** — `headwaters models verify-tools` (optionally `--model`, `--force`) — and on
`headwaters models refresh --verify-tools`. It does **not** run in the request path and does not
run in the background TTL refresh (`refresh_if_stale`) or a plain `models refresh`
(`models.tool_probe.on_refresh` defaults to `false`), because probing loads a model (up to the
240 s cold-start bound) and a startup path must not wait for that. The observation is stored in
a new `capability_probes` table and overlaid on candidates at routing time, so a later
`models refresh` cannot resurrect an advertised-but-broken capability.

#### Slice B — wire `ModelsRules.overrides` into routing

Apply `ModelOverride` (`tier`, `scores`, `tools_ok`, `json_ok`, `ctx`) last, after catalog facts
and scoring, exactly as the docstring in `headwaters/core/rules.py` promises. A fresh
`rules.yaml` edit takes effect on the next request (the rules provider already re-reads the file
per request; the watcher is `headwaters/core/rules_watch.py`). Tests prove an override changes
the chosen model and that an invalid override is rejected with a clear error.

#### Slice C — an honest `pull_model` hint

Never recommend pulling a model that is already installed or already chosen. When the shortfall
is capacity tied to tool schemas, say so in the hint text. HDW-511 owns the composition-honest
`local_unavailable` error message; this slice only makes the hint truthful.

#### Slice D — the gateway answer footer

The user's requirement, verbatim: *"the response have a footer saying what model answered ...
also in the footer we may add additional details related to cost, so a footer mechanism would be
needed for that as well"*.

- Extensible mechanism, not a hardcoded string: `gateway.footer` in `rules.yaml` with
  `enabled` and a list of `fields`.
- Fields: `model`, `tier`, `tokens` (prompt+completion), `cost` (USD, with an honest `free`
  form for local), `latency`.
- **Default OFF** (`gateway.footer.enabled: false`): no existing client, host or test suddenly
  sees extra text in the assistant message. The mechanism is covered by tests both off and on.
- Chat-host visible: non-streaming gets the footer appended as the tail of the assistant
  message content, one line, plain text, preceded by a blank line; streaming emits it as a
  final content delta before the existing finish/usage chunk.
- Never appended when `finish_reason` is `tool_calls`; never on an error response.
- Never counted in usage and never counted as model output.
- Data comes from the existing `_headwaters_meta` metadata (moved to
  `headwaters/gateway/shared.py` so both faces use it), extended with tokens, cost and latency;
  cost is not re-derived in the gateway.
- Anthropic mirrored when it does not corrupt block structure (see Part 3).
- The footer becomes part of the conversation history a host may echo back; a header
  (`X-Headwaters-Model`, already emitted) is the invisible alternative. This ticket implements
  the body footer only.

### Non-goals

Do not touch summer-engine, do not change Cline's configuration, do not implement progressive
disclosure for third-party MCP servers, do not push or merge, do not edit
`headwaters_ticket_packets/HDW-511.md` (another ticket owns it).

### Slice A detail codes (stable, never request text)

| detail | meaning | record? | `tools_ok` |
| --- | --- | --- | --- |
| `structured` | matching `tool_calls`, empty content | yes | `true` |
| `structured_with_text` | matching `tool_calls`, non-empty content | yes | `true` |
| `wrong_tool` | a tool call, but not the offered name | yes | `false` |
| `call_as_text` | no `tool_calls`; content is the call as JSON text | yes | `false` |
| `text_answer` | no `tool_calls`, content is prose | yes | `false` |
| `skipped:<why>` | disabled/limit/lock/scope/recent | no | untouched |
| `error:<code>` | provider/executor failure | no | untouched |

### Footer shape

```
<assistant text>

Headwaters: model=qwen3:8b tier=local tokens=1204+88 cost=free latency=812 ms
```

Rules:

```yaml
gateway:
  footer:
    enabled: false            # default: the body stays byte-clean
    fields: [model, tier, tokens, cost, latency]
```

- `cost` prints `free` for a local tier (no price exists), `$0.0012` for a priced model, and
  `unknown` when no cost was computed. It is never invented.
- The footer is appended after `usage` is computed, so it can never enter the token counts.
- `finish_reason == "tool_calls"` → no footer (`_chat`, `_chunks`, `_message`, `_stream` all
  check before appending). Error responses never reach the footer path.
- Anthropic: the footer is appended to the text block that already exists (or the empty text
  block), and on the stream inside the open text block before `content_block_stop`. With a
  `tool_use` answer the footer is skipped, so block structure is untouched. It can carry the
  line without corruption.

### Accept when

- `headwaters models verify-tools` marks `qwen2.5-coder:14b` `tools_ok=0` with `call_as_text`
  recorded, and `qwen3:8b` `tools_ok=1` with `structured`; a later `models refresh` keeps the
  routing outcome.
- An override in `rules.yaml` changes the next decision without restarting the daemon.
- `headwaters pick --tools --tokens 15000 --scope local` no longer suggests pulling the model it
  chose.
- With `gateway.footer.enabled: true` a real gateway answer ends with one footer line; with the
  default it is byte-identical to today.
