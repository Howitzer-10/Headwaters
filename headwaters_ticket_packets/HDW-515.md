# HDW-515 — two OpenCode providers, two endpoints: `opencode` and `opencode-go`

Base: `dfb1641` (HDW-514). Report: `docs/reports/HDW-515.md`. Follow-ups: `FU-515-n` there.
Units are tokens, not pages: this packet is the whole brief.

## Part 1 — context pack

### 1.1 Why this ticket exists

HDW-514 registered cloud providers as data (`catalog.providers` rows, `Registry`,
`KeyStore.providers()`) and deliberately shipped **no** OpenCode row, on assumption **A-OC-3**:
"no evidence a key changes the 403 for free models." That left the whole OpenCode surface
unreachable from Headwaters even though a person can authenticate to it.

A user has now shown, from the client's own UI, that OpenCode exposes **two** products with
**two** API endpoints, not one:

| product | auth as observed | free models observed in the picker |
| --- | --- | --- |
| `opencode` (Console, account-authenticated) | no static key; an OAuth session (`providers.json.oauth-*.lock`) | Beam Free, Crouton Alpha Free, DeepSeek V4.1 Flash Free, Flint 40B Free, GLM-5.3-Flash Free, MiMo-V2.6-Flash Free, Nemotron 3 Ultra Free, Nemotron 3.5 Lightning Free, Nemotron 3.5 Super VL Free, Pulse Alpha Free (10) |
| `opencode-go` (Go plan) | static 51-character key | Beam Free, Iceman Contributor Free (2); currently used with the paid model DeepSeek V4.1 Flash |

The user confirmed the two are **different endpoints** and that `OPENCODE_API_KEY` is the one
environment variable for both. This ticket registers both as catalog rows with their own base URL,
model-list URL, key check and tier, and corrects A-OC-3 instead of ignoring it.

### 1.2 Evidence treated as given (UI / on-disk, dated 2026-11-03)

- Cline v0.0.49 provider picker: Provider `OpenCode`, model search `free` → the 10 models above;
  Provider `OpenCode Go`, model search `free` → the 2 models above.
- `%USERPROFILE%\.cline\data\settings\providers.json`: the `opencode` entry has **no `apiKey`**
  (an account/OAuth session; a `providers.json.oauth-*.lock` file exists), the `opencode-go`
  entry **has** a static 51-character key.

These are UI and on-disk observations, **not** API facts. Nothing in this ticket may depend on a
base URL, header shape, list endpoint or free-tier signal that Part 3 did not verify. The
credential files themselves are out of bounds (secrets rule, §1.6).

### 1.3 A-OC-3, corrected (binding restatement)

Old text (`docs/ASSUMPTIONS.md`, A-OC-3): free models exist, the docs say they require OpenCode,
"**no machine-readable list endpoint found**", `whitelist`/`blacklist` filter the picker.

Corrected text, and what HDW-515 writes into `docs/ASSUMPTIONS.md`:

- The free models are **real, publicly listed and priced at zero** — there **is** a machine-readable
  listing (`GET /inference/v1/models`), so the "no list endpoint" clause was wrong.
- They are **account-gated, not anonymity-gated**: the gate is *the OpenCode client itself*. The
  Console docs say verbatim that free-tier chat models "are only available from within OpenCode;
  other clients receive HTTP 403, even with an API key."
- Therefore the HDW-514 decision (do not call them, do not offer them) was **right for the wrong
  reason**: the probe was unauthenticated, but a static key would have got the same 403. What
  changes in HDW-515 is not reachability of the free tier; it is that the **paid** Console models,
  the **Go** plan models and a **verified model list** become available, and that the free ids are
  filtered out by rule instead of by the absence of a provider row.
- A key that does reach the free tier from outside the client remains **unverified** — see FU-515-1.

### 1.5 What the evidence does not support

- It does **not** support marking either provider `free_cloud`. `opencode` is pay-as-you-go and its
  free ids are unreachable from outside the client; `opencode-go` is a subscription whose included
  free models cost $0 per call but not $0 to the person (the D-tier rule: included-in-plan is not
  free, same reading as Hugging Face included credits).
- It does **not** support a Console free-tier key. No key was present in the environment for this
  ticket (recorded in `docs/SDK_FACTS.md` as "not verified: no key present"), so the decisive
  keyed probe is a follow-up, not a silent assumption.
- The observed 10 free models are UI truth; the listing shows 9. The list is the authority for
  code, the observation is the authority for "these are not fiction".

### 1.6 Out of scope (report as follow-ups only)

OAuth / device-flow login in Headwaters; reading or reusing the person's Cline/OpenCode credentials
(hard rule, below); pruning, router/ladder changes, dashboard and tray surfaces (HDW-503/504 own
them); the `00_INDEX.md` row; pushing or opening a PR; flipping `features.paid_scopes`.

**Secrets, hard rule.** Never read, print, log, copy or commit a credential: not
`providers.json` values, not Notepad `API-Keys.txt`, not any key file. A probe refers to the
environment variable by name (`Authorization: Bearer $env:OPENCODE_API_KEY`), never to its value,
and a key never reaches a log, a report or a commit. Absent key ⇒ "not verified: no key present"
in `docs/SDK_FACTS.md`, and the ticket does **not** block.

Accept when:

- Both rows validate, and `Registry.from_catalog` yields two entries whose `base_url` and
  `models_url` are **different from each other** and each is the URL verified in Part 3.
- `ProviderEntry` can express a listing URL that is not `base_url + models_path` (the OpenCode
  listing is at `/inference/v1/models`, the chat base at `/inference/openai/v1`; `/models` under
  the chat base is 404). No provider may be registered with a guessed listing URL.
- Two providers may share one `env_var`: the catalog's cross-reference check no longer rejects a
  repeated variable, and `KeyStore` keys every record by **provider name**, so saving a key for
  `opencode` never answers for `opencode-go`. An environment variable reaches both (one variable,
  two products — that is the observed reality), a stored key does not.
- `provider_name("OPENCODE_API_KEY")` is deterministic: the **first** catalog entry that declares
  the variable wins (`opencode`), never "last row parsed".
- `opencode` is no longer a reserved name and is no longer in the keyless set: it needs a key now.
- A model the entry's `skip_id_pattern` excludes is refused by `TargetBuilder` with
  `provider_unsupported` rather than called for a 403 (defence in depth, data-driven, no hard-coded
  slug).

## Part 3 — per-provider verification protocol

Before any code depends on a provider, each row below must be filled from the provider's **own**
public docs or a live probe. A field that cannot be filled is `null` in the catalog, not a guess.

1. **Base URL (chat).** The OpenAI-compatible root the client actually posts to. Cross-check with
   the docs' path examples.
2. **Auth style.** Header shape and whether the key is a static bearer, an account session, or
   both; record which one Headwaters can hold.
3. **Model-listing endpoint.** Fetch it anonymously and with a bogus bearer. A listing that 401s on
   a bogus key is also a key check; a listing that is 200 anonymously is not a free-tier signal.
4. **Free-tier signal.** Which field marks a model free (`cost` 0/0, `is_free`, `:free`), and
   whether the provider documents that the marker is reachable by a key-holding outside client.
   Only a documented, reachable free call may produce a `free_cloud` row.
5. **Rows before code.** One `docs/SDK_FACTS.md` row per verified fact, and a
   `docs/ASSUMPTIONS.md` row that points at it, in the same commit as the code that reads them.

Protocol results for this ticket are in §1.4 and in `docs/SDK_FACTS.md` ("OpenCode providers
(HDW-515)"); the one unfilled field (does a real Console key reach the free ids from outside the
client) is FU-515-1 and is recorded as unverified rather than assumed.
