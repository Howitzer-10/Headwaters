## Part 2: Ticket

### HDW-516 · Cloud-first descending order
**Model** Sonnet · **Effort** Medium · **Depends** 513 (unmerged; interleaving must land first), 112, 113, 114 · **Class** core, no ★ · **Refs** v3.3 §A (routing model), docs/reports/HDW-513.md

**Goal:** make the *ordering of tiers* a configured preference instead of a fixed policy, so a
user who wants the VRAMWeave-style "best tier first, descending" cascade can have it, without
taking today's fair round-robin away from anyone who does not ask.

This is an **ordering function plus a preference field**. It is not a new router, not a new
attempt loop, and not a new tier.

### The decision this ticket encodes

> Candidate order inside one request is produced by one of two named strategies: `interleave`
> (today, HDW-513: one attempt per tier before any tier repeats) or `descend` (exhaust the
> preferred tier before moving on, in a configured direction). The **default is `interleave`**,
> byte-for-byte today's behaviour, so no existing test, recipe or user's routing changes on
> upgrade.

#### D1 · The config surface (one field, one direction, one registry)

New keys in `headwaters/core/rules.py`, in the existing `RouterRules` block, plus one exported
registry of the names:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `router.tier_order` | `Literal["interleave", "descend"]` | `"interleave"` | `interleave` = today (HDW-513). `descend` = exhaust a tier before leaving it. |
| `router.tier_direction` | `Literal["cloud_first", "local_first"]` | `"cloud_first"` | Only read when `tier_order: descend`. `cloud_first` walks paid → openrouter_auto → free_cloud → local; `local_first` walks the reverse. |

Rules of the surface:

1. **Both names live in one exported tuple next to the type**, next to the existing
   `Strategy` literal (`headwaters/core/rules.py:17`): e.g. `TIER_ORDERS: tuple[str, ...]` and
   `TIER_DIRECTIONS`, with the pydantic `Literal` derived from them so the schema, the docs and
   the validators cannot disagree. Everything that prints a strategy today — status page, CLI
   status, pick report, MCP scope tool, MCP descriptions, `catalog/rules.schema.json` — imports
   the same tuple instead of re-typing strings. `headwaters/core/rules_edit.py:32`
   `EDITABLE_KEYS` gains `"router.tier_order"` and `"router.tier_direction"` only if the existing
   dotted-key support covers nested keys; if it does not, they stay hand-edit-only and the report
   says so (do not build a second nested-edit mechanism for two keys).
2. **`tier_direction` is ignored, not rejected, under `interleave`.** A user who switches back to
   `interleave` must not lose their direction choice, and the validator must not make two keys
   mutually exclusive for cosmetic reasons.
3. **Default unchanged, stated explicitly:** with no rules change, `tier_order` is `interleave`
   and the code path is the HDW-513 path. No existing test or recipe shifts, and the ticket adds
   a test that asserts the default resolves to `interleave`.
4. **The tier walk is data, in `scope.py`.** The ordered walk the direction selects comes from one
   tuple next to `SCOPE_TIERS` (`headwaters/core/scope.py:43-48`), the module that already owns
   `TierName` and the tier groupings. `local_first` is that tuple reversed, not a second list.
5. **Degenerate cases are already expressible as scope, and stay there.** "free only" is
   `default_scope: free` (`SCOPE_TIERS["free"] = {free_cloud, local}`) and "local only" is
   `default_scope: local` (`{local}`, fail-closed). This ticket **does not** add
   `tier_order: free_only`. Two mechanisms for one restriction is how they drift apart; the
   accept-when lines below prove the composition instead.

#### D2 · The ordering function

`headwaters/core/policy/ladder.py` gains one function next to `interleave_tiers` (*(513)*, `ladder.py:100`):

```
descend_tiers(entries, direction) -> list[Entry]
```

- **Stable** sort of `entries` by the tier's index in the direction's walk. Stability is the
  contract, not an accident: rung order **inside** a tier is the ranking (and the floor logic) of
  `build_ladder`, so a non-stable sort would silently rescore the whole ladder.
- Pure: same input, same output, no rules/db/clock reads. It takes the direction as an argument;
  it does not read `ctx.rules`.
- Entries whose tier is not in the walk keep their relative order **at the end**. That is a
  defensive branch — `TierName` is a closed literal — and it is tested so a future tier cannot be
  silently dropped.

`build_ladder` ends with a three-line choice (`ladder.py:180` *(513)* becomes):

```
return interleave_tiers(unique, req.tier_attempts) if order == "interleave" else descend_tiers(unique, direction)
```

`req` is extended the way HDW-513 already extended it (`headwaters/core/policy/types.py:23-31`,
`PolicyRequest`): the field travels on the request, so `_redecide`
(`headwaters/core/router.py:427-435`) keeps the same preference on the retry without the router
learning anything new.

**What `descend` does to the rotation.** `interleave_tiers` uses `tier_attempts` to rotate. Under
`descend` the tried tiers are still passed (the signature does not change) and are still honoured
by the exclusion filter that runs before `build_ladder`; the descending walk simply does not use
them for rotation, because "continue down the list" and "rotate back up" are different policies.
`descend` therefore needs no new parameter and the 513 signature is untouched.

#### D3 · Interaction with pin and `pin_strict`

- A pin is resolved **before** the ladder (`decide.py:39`, called at `decide.py:118-125`), so the
  ordering function never sees the pinned candidate. A pin on a local model under
  `tier_order: descend, tier_direction: cloud_first` still routes **local**. Tested.
- `pin_strict` still fails as itself instead of failing over (`router.py:410`); the fallbacks list
  built by `decide.py:124` is still reported, so a non-strict pin's alternates are still visible in
  the order the preference asks for.
- The preference does not weaken the hard filter: a pinned model that does not pass it is still
  `pin_rejected` (`decide.py:39`), unchanged.

#### D4 · Interaction with walls and quotas

- Skip, never descend-into. Wall and quota state enters through `Availability`
  (`quotas.py:158-162`) and is applied by the hard filter (`filters.py:99-100`) **before** the
  ladder exists. An exhausted tier is not in `kept`, so no ordering can retry it, and the reason
  string `unavailable_<status>` still names it. Tested with a free-tier wall under `cloud_first`.
- The wall/prompt rule is unchanged: `QuotaTracker.record_wall` (`quotas.py:254-299`) still returns
  `retry`/`cascade` exactly as today, `WallsRules.cascade_if_wait_over_s` still decides it, and
  nothing in this ticket turns a cascade into a silent tier downgrade. When the ladder runs out,
  the existing end-of-request error (`router_failures.terminal_message`, *(513)*
  `headwaters/core/router_failures.py`) is the only exit. **D19 check:** descending to a weaker
  model is a *config choice the user made*; it is never presented as the strong model answering.
  `RouteDecision.below_floor` and `verify_required` (`types.py:41-55`) keep being set by the same
  code, and the ticket adds a test that `descend` **cannot** clear either flag.
- `rpm`/`rpd` counting is untouched: `count_request` (`quotas.py:335`) is called from
  `router.py:375` once per attempt, as today.

#### D5 · Interaction with never-re-pick-a-failed-model (HDW-513)

- Exclusion wins over ordering. `run.excluded` (`router.py:418`, `:538`) is filtered before
  `decide`, so `descend` can never re-propose a model that already failed in this request, even if
  it is the only model left in the preferred tier. Tested: fail the top paid model on attempt 1
  under `cloud_first`, and attempt 2's ladder does not contain it.
- Exclusion stays **per request and not a cooldown** — the HDW-513 property (a model walled in
  request N is available in request N+1) is preserved, and this ticket asserts it rather than
  restating it.
- `router.max_attempts` still bounds everything. Under `descend`, `max_attempts: 4` means four
  attempts **in total**, not four per tier. This is deliberate (it is a spend bound) and is
  asserted by a test, because "exhaust the whole tier first" reads like it might mean more calls
  than before.

#### D6 · Where the strategy is expressed (D18)

One registry, six readers. The names go in `headwaters/core/rules.py`; then:

| Surface | What it must read |
| --- | --- |
| `catalog/rules.schema.json` | regenerated with `uv run python -m headwaters.core.rules_io --write` (see `docs/SDK_FACTS.md`, Windows and repo tooling) — never hand-edited |
| `headwaters/control/status_page.py:57,75,117,180,250` | the same tuple; the status line prints `interleave` / `descend (cloud_first)` |
| `headwaters/cli/cmd_status.py:156,179` | the same tuple |
| `headwaters/cli/pick_report.py:37,85` | the same tuple, and the fallback order it prints is the ladder order |
| `headwaters/mcp/tools/scope_tool.py` + `headwaters/mcp/tools/descriptions.py:57` | the same tuple; a plan-change line when the value differs |
| `headwaters/features/tray`, `headwaters/features/dashboard` (★, unbuilt — HDW-503/504) | nothing to change today; the requirement recorded here is that they import the registry, not copy the strings |

`docs/` gets the two keys documented wherever `strategy` is documented today, in one commit with
the rules change.

#### D7 · Failure and stop rule (unchanged, restated so nobody "improves" it here)

A wall still records, still retries or cascades per `WallsRules`, still stops the request when
`max_attempts` is spent, and still tells the user in the terminal message which tiers were not
tried. **Descending never spends on a tier the user did not allow.** A paid model whose key is
missing or whose balance is walled is `unavailable_*` from the hard filter, exactly like any other
wall, so `cloud_first` cannot reach it — the ladder descending into a paid tier does not create a
call, a key, or a purchase. That path is unchanged by this ticket, and the ticket asserts it
(test 8 plus the D19 test 11: a weaker model that answers still reports itself as weaker).

#### D8 · What this is NOT

- **Not a verifier.** Nothing checks whether an answer is any good. That is HDW-517, and it is a
  separate ticket with a separate problem (provenance of a pass/fail signal).
- **Not a change to tier membership or to scope.** `SCOPE_TIERS`, `FREE_TIERS`, the catalog's tier
  assignment, the Private lock, the project rule and secret detection all behave exactly as today.
  The new field chooses an **order** over the tiers a scope already allowed.
- **Not a new router, attempt loop, retry policy, budget, or ledger event.** One ordering function
  and one preference field.
- **Not a new strategy.** `strategy` (cost_saver / quality_first / primary_first) keeps its meaning
  as ranking *inside* the ladder and composes with `tier_order`: strategy decides where a candidate
  sits within its rung, `tier_order` decides which tier is consumed first. Note the near-collision:
  `primary_first` moves the configured paid primaries to the front rung but does **not** change tier
  order, and the ticket adds a test that pins that distinction.
- **Not a fairness fix for `descend`.** Under `descend`, a preferred tier that can serve everything
  will serve everything, and cheaper tiers may starve. That is the requested capability, not a bug;
  `interleave` remains the default and remains the anti-starvation answer.
