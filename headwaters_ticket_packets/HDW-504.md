## Part 2: Ticket

### HDW-504 · Tray app ★
**Model** Sonnet · **Effort** Large · **Depends** 201, 503 · **Class** ★ · **Refs** v3.1 §C7, v3.3 §C
**Build:** the tray is the front door: it shows what is happening, switches scope, and opens the
dashboard straight at the keys.
- `pystray` icon: green / amber / red, plus **purple lock** for Private Mode.
- Right-click menu (exact order, exact wording — see "Menu" below).
- Rate-limited toasts on tier switches.
- Starts with the daemon; `headwaters tray` starts it by hand.
**Accept when:** the Windows manual checklist passes; every menu action is covered by a unit test
through the daemon internal API; and no menu label can ever contain a secret (asserted).

#### Dependencies (the only dependency change in this ticket)

Add `pystray` and `Pillow` to `[project] dependencies` in `pyproject.toml` and regenerate
`uv.lock` with `uv lock`. Nothing else is added or bumped: no Qt, no wx, no `pystray` backend
extra, no notification library. Icon images are drawn at runtime with `PIL.ImageDraw` (a filled
circle plus a lock glyph) — no bundled PNGs, no shell icon extraction, so there is nothing to
package and nothing to lose on a fresh install.

#### Menu (exactly these items, in this order)

1. **Status line** — a disabled, non-clickable item that reads the live state in one line:
   the effective scope, the tier in use, the warm model, or **daemon not running**. One line; if
   two facts matter, the scope and tier come first.
2. **Scope** submenu: `auto`, `free`, `local`, `cloud`, with the current one radio-checked.
   Switching goes through the **daemon internal API** (`POST /v1/scope`), never the CLI, so the
   running daemon applies it immediately and reports back; if the daemon refuses (a lock is on,
   or the paid tier is out of scope) the tray stays on the old value and shows the reason.
3. **Private Mode** — a checkable item. On = Private lock on, **and** a purple lock appears in
   the icon. Same internal API path as scope.
4. **Keys** submenu: one item per provider reading **`<Provider> — set`** or
   **`<Provider> — not set`**, each opening the dashboard keys section at that provider's anchor
   in the default browser; plus **Manage keys...**, which opens the section without an anchor.
   The provider list is the daemon's (`GET /v1/keys`), which reads `KeyStore.entries()` — the
   same source the dashboard page uses, so a provider registered later (HDW-514) appears with no
   tray change.
   **The menu must never contain a secret, a masked value, or any part of a key.** The tray
   parses `provider`, `alias` and `source` only and drops everything else from the reply; if the
   daemon sends a `masked` field it is dropped unread. A unit test asserts the reply's masked
   value and the stored secret appear in no label.
5. **Open dashboard** — `DaemonInfo.dashboard_url`; disabled when there is no daemon.
6. **Doctor** — runs the doctor the CLI runs (same code path, in-process), and shows the summary
   rather than making the user retype the command.
7. **Restart daemon**.
8. **Quit** — stops the tray only. The daemon is a separate process and keeps running; say so in
   the item's tooltip if the menu supports one.

#### Icon states

- **Green** — healthy: daemon up, and nothing below is true.
- **Amber** — degraded: daemon up **but** no cloud provider can serve — no key is set (no
  provider in `KeyStore.entries()` has a source other than `not set`) **and** no registry provider
  works anonymously (HDW-514 may ship one; if it does, a keyless install is healthy, not
  degraded) — **or** an active wall (`active_walls` is non-empty), **or** routing is below floor
  (the last decision's `below_floor` is true).
- **Red** — daemon down (`read_info()` is absent or the health call fails), **or** the last
  request failed.
- **Purple lock overlay** — Private Mode on, drawn *over* whichever colour is current, so "amber
  + purple" is a real state.

Refresh on a timer of **about 2 seconds** against the daemon internal API. The timer must not
stack requests: skip a tick while the previous one is in flight, and treat a timeout as
"daemon down" for that tick without blocking the menu.

#### What the tray reads (and what must be added for it)

Today `GET /v1/status` returns pid/version/uptime, ports, `scope`, `private_lock`, `airplane`,
catalog, `keep_warm` and `last_refresh` — **no warm model, no tier in use, no walls, no
below-floor flag and no per-request outcome**, so the status line and the amber rule cannot be
computed from it. Extend the payload rather than having the tray guess: add a small block (for
example `tray: {tier, warm_model, walls, last_status, below_floor, keys_set}`) built by the
daemon from the same core helpers the status page uses. Add `GET /v1/keys` returning providers
and aliases with `source` only (no masked values, no secrets) — the same data shape the dashboard
renders, minus the mask.

The tray is a separate process: it reads `read_info()` and `read_token()` from
`headwaters.core.daemon_info` and sends the bearer token like every other internal client. A
missing daemon is a normal state (red icon, most items disabled), not an error dialog.

#### Start and autostart

- **The tray starts with the daemon.** The existing logon task already runs `headwaters start`
  (`headwaters/packaging/autostart.py`: `TASK_NAME = "Headwaters"`, `DEFAULT_ARGUMENTS =
  ("start",)`, toggled by `python -m headwaters.packaging.autostart --enable|--disable`). Do not
  add a second scheduled task: the daemon starts the tray as a child when the tray flag is on, so
  the existing on/off toggle still controls both.
- **`headwaters tray` starts it by hand** (a Typer command). With the tray flag off, the command
  says how to turn it on instead of failing silently.
- The tray inherits Private Mode and scope state from the daemon at startup — never from a file
  of its own — so two surfaces cannot disagree.

#### Tests

- Menu construction and every action, unit-tested through the daemon internal API layer with a
  fake transport (`httpx.MockTransport`): scope switch posts the right path/body, Private toggle
  posts the right value, **Open dashboard** and every **Keys** item build the right URL,
  **Quit** stops the icon. **No real icons and no real browser launches**: inject the icon object
  and an `opener(url) -> bool` callable, and assert on the URL instead of opening it.
- Icon state: render the image with PIL for each fixture state and assert the centre pixel is
  green/amber/red, and purple-over when Private Mode is on. No notification-area interaction, so
  the tests run headless in CI.
- No-secret assertion: with a fake `/v1/keys` reply that carries a masked value and a fake store
  holding a real secret, no label contains either.
- URL shape depends on HDW-503's anchors: `/?section=keys#keys-<provider>` and `/?section=keys`.
  If that ticket lands without the anchors, the anchors are the blocker, not a tray fallback.

#### Out of scope

Per-pixel icon art, autostart changes (the toggle already exists), and any dashboard work: the
keys section is HDW-503 and the tray only links to it.

### Excerpt: v3.1 addendum §C7

#### C7. Packaging and distribution
- **Installer:** Inno Setup `.exe` that bundles the `uv` binary plus a locked `uv.lock`, and creates a private venv under `%LOCALAPPDATA%\Headwaters\runtime`. No admin rights are needed for a per-user install.
- **Avoid PyInstaller one-file builds** (frequent Defender false positives). If you freeze the app later, prefer Nuitka.
- **Code signing:** sign the installer and launcher shims, so SmartScreen doesn't warn buyers. Budget for a code-signing certificate or a cloud signing service, and verify eligibility for individual developers in your country.
- **Autostart:** Task Scheduler "At log on" task for the current user (no admin rights), with an on/off toggle in the wizard.
- **Tray:** `pystray` (Windows notification area) with green/amber/red status and toast notifications on tier switches (optional, rate-limited).
- **Secrets:** `keyring` with the Windows Credential Manager backend.
- **itch.io:**
  - Ship a `.itch.toml` manifest with launch actions ("Open Control Center", "Run Setup Wizard", "Doctor").
  - Push with `butler push <dir> <user>/<game>:windows-lite` / `:windows-pro`.
  - The installer and the itch app install should both work. Detect an itch-managed install and avoid self-update conflicts.
- **Uninstaller:** removes the scheduled task, the runtime and, optionally, state and keys (ask first).


### Excerpt: v3.3 addendum §C

### C. Precedence and switching
```
effective_scope = intersect(
    private_lock ? local : ANY,
    project_rule (.headwaters.yaml privacy: local|free|any),
    secret_detected ? local : ANY,        # configurable: local | refuse | off
    requested_scope (picker model / MCP param),
    default_scope (rules.yaml) if nothing requested
)
```
- A tighter scope always wins. Only the user can loosen a lock, and never mid-request. Project rules can only tighten.
- If the intersection is empty or can't be satisfied, return a structured error with a fix (e.g. "pull qwen2.5vl:7b", "disable Private lock in tray").
- **Switch surfaces:**
  - Picker model (gateway / VS Code extension)
  - Tray toggle "Private Mode" (purple lock icon)
  - VS Code status bar
  - CLI `headwaters scope <auto|free|local|cloud>` / `headwaters private on|off`
  - MCP `set_scope` / `set_private`
  - Prompts `/headwaters-local`, `/headwaters-free`, `/headwaters-auto`
  - Optional global hotkey
- MCP tools accept `scope` and **inherit** the effective scope from locks and project rules. In MCP-only setups, `set_scope` sets the default.


### Normative: what exists today (verified in the repo at packet-writing time)

Re-verify before coding; where the code and this section disagree, the code wins and the
difference goes in the report as a deviation.

- **Daemon internal API** (`headwaters/gateway/server.py`, `build_app` + `GuardedApp` bearer
token): `GET /health` (no token), `GET /v1/status`, `POST /v1/reload`, `POST /v1/shutdown`.
There is **no scope endpoint and no keys endpoint** — this ticket adds `POST /v1/scope` and
`GET /v1/keys`, and extends the `/v1/status` payload. `daemon-is-a-root` and
`daemon-no-direct-web-framework` still hold: the routes live in `headwaters.gateway`, the
daemon only wires them.
- **Writing settings** already has one implementation and this ticket reuses it:
`headwaters/core/rules_edit.py` (`EDITABLE_KEYS` = `default_scope`, `private_lock`,
`strategy`; `set_setting(...)`), which is what `headwaters scope …` / `headwaters private …`
use, with `headwaters/cli/daemon_sync.py` (`confirm`) telling the running daemon to reload.
`POST /v1/scope` applies `set_setting` and then the same reload-and-report path, so the tray,
the CLI and the dashboard cannot disagree about what "scope is local" means. A key alone does
not loosen a lock: Private lock and project rules still win (v3.3 §C above).
- **`headwaters/core/daemon_info.py`**: `read_info()`, `read_token()`, `DaemonInfo.api_url`,
`DaemonInfo.dashboard_url` (`http://127.0.0.1:{ports.dashboard}/`, or `None` when the dashboard
is off), `DaemonPorts(api, gateway, dashboard)`. The token lives in `daemon.token` next to
`daemon.json`; the tray reads both and never prints either.
- **`headwaters/packaging/autostart.py`** (note: `headwaters/packaging/`, not the repo-root
`packaging/`, which holds butler/Inno/itch assets): `TASK_NAME = "Headwaters"`,
`TASK_PATH = "\Headwaters"`, `DEFAULT_ARGUMENTS = ("start",)`, `task_xml`, `create`,
`status`, `apply`, and the entry point `python -m headwaters.packaging.autostart
--enable|--disable|--delete|--status`. The tray must work with that toggle, not around it.
- **`pyproject.toml` `[project] dependencies`** today: `cryptography`, `httpx`, `jsonschema`,
`keyring>=25.7.0`, `litellm==1.106.6`, `mcp>=2.3,<3`, `nvidia-ml-py`, `pathspec>=1`,
`platformdirs>=4.14`, `psutil`, `pydantic>=2.13`, `pyyaml>=6`, `starlette`,
`tree-sitter-language-pack`, `typer>=0.27.3`, `uvicorn`, `watchdog>=6`. Neither `pystray` nor
`Pillow` is present, so both are genuinely new; `httpx` is already there for the internal API
client.
- **`headwaters/features/`** holds only `__init__.py` today: this ticket creates the tray as a
★ module (the icon and menu) plus a CLI command, and the daemon starts it. `pystray` and
`Pillow` are allowed in a feature module; web frameworks are not
(`web-framework-only-in-gateway`), and nothing outside the daemon may import
`headwaters.daemon`.

### Normative: dependency on HDW-503

The **Keys** submenu links into the dashboard, so this ticket depends on HDW-503 for:

- the dashboard URL (`DaemonInfo.dashboard_url`) being served at all;
- the anchors `#keys` and `#keys-<provider>` and the `?section=keys` reordering;
- the provider list being the key store's list (`KeyStore.providers()`), which the daemon
exposes here as `GET /v1/keys`.

Do not build a second keys UI in the tray and do not put a value in the menu: the tray shows
**set / not set** and opens the page. If HDW-503 is not in the tree yet, the Keys submenu still
ships (labels are honest), and the anchors are a follow-up line in the report rather than a
guess.
