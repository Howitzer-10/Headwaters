# HDW-518 — Local model keep-warm heartbeat

**Status:** packet / design — not implemented.
**Depends on:** nothing new (no routing change). Interacts with HDW-516/517 only in that all three
touch the local tier — none of them shares state with this ticket.
**Owner directive:** "the first real request after idle should not pay a cold model load" — a
daemon-owned background heartbeat that sends a minimal request to the configured local Ollama model
with `keep_alive` so the weights stay resident; opt-in, off by default; zero cloud traffic; no effect
on routing, walls or accounting; must not appear in the request/cost ledger as a user request; back
off when the machine is idle or on battery; stop cleanly on shutdown; not resurrect after being
turned off. (The 15-minute `keep_alive` figure in the owner's brief is cited there as prior art from
another product; it is **not** a verified SDK fact here — see P1.)

> **Read this first: most of the mechanism already exists.** A periodic keep-warm tick, running in
> the daemon, pinging Ollama's `/api/chat` with an empty message list and the configured
> `keep_alive`, is already built (HDW-201). Part 1 §3 lists exactly what is already true and is
> therefore **not** in scope. What this ticket adds is: one configurable interval, two opt-in
> modes, an idle backoff, and a set of tests that freeze the "harmless" properties that are
> currently true only by accident of construction.

### 1. What the owner is asking for, in routing terms

Nothing in the routing path. The ask is a **residency** property: after N minutes of no requests,
the next request to the local model should not pay the model-load cost. It is a latency and
predictability feature, not a policy feature — and that distinction is the reason every interaction
below is "must not change X" rather than "must choose X".

### 4. What is genuinely missing

1. **No interval knob.** The interval is hard-derived as `keep_alive/2` (`keepwarm.py:82-88`); a user
   cannot say "ping every 5 minutes" or "ping every 20 minutes".
2. **No idle backoff.** `_blocked()` covers GPU-busy and battery only (:103-111). A machine that has
   been idle for hours still pings — keeping a GPU warm that nobody is using.
3. **`auto` cannot recover from a cold device.** With the default `keep_warm_model: "auto"`, if
   nothing is loaded there is nothing to re-arm (`:129-131`) — so after a laptop sleep, a daemon
   restart, or another process evicting the model, the next request pays the full load and keep-warm
   will not bring it back. An explicit model *does* load when the device is empty (`:135-138`), but
   that behaviour is unstated in the docs and untested.
4. **The harmless properties are untested.** Every "already true" row in §3 is true by construction,
   not by a test. A future refactor that routed the ping through the router would break the ledger
   guarantee silently.

## Part 2 — Design

### D1. Scope decision: extend the tick, do not add a second one

A new heartbeat task would duplicate a scheduler that already exists (`service.py:305-313`, :406).
The packet therefore extends `KeepWarm.tick()` and its config, and adds **no new background task**.
The only new behaviour at the daemon level is that the interval becomes a function of two config
keys instead of one derivation.

### D2. Config surface

All under `tiers.local` (the `LocalTier` model, `rules.py:96-111`), all default-off:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `keep_warm_heartbeat` | bool | `false` | Opt in to the heartbeat mode: a configurable interval plus the cold-device loader rule |
| `heartbeat_interval_s` | float | `0.0` | `0` = derive (`keep_alive`/2, floor 30 s — today's value). Must be strictly less than the parsed `keep_alive` when set |
| `heartbeat_idle_backoff_s` | float | `0.0` | `0` = off (never back off). After this many seconds with no routed request, the tick stops pinging and logs once; it resumes on the next routed request |

Reused, unchanged: `keep_alive` :101 (the window we ask Ollama to hold), `keep_warm_model` :102
(`auto` | `off` | a model name — the existing selector, not a new one).

**Why `keep_warm_heartbeat` is a flag rather than "just add the keys":** the defaults for the three
new keys are `false`/`0`/`0`, so a config that does not mention them behaves exactly as today
(D7). Nothing about the existing `keep_warm_model: auto` behaviour changes — including its
on-by-default-ness (K13). **The packet does not flip that default**; see §D3.

### D3. The "opt-in, off by default" clause — resolved honestly

The owner asked for opt-in/off-by-default. The existing tick is already on by default whenever a
model happens to be loaded (K13), and flipping it would be a silent behaviour change for every
existing install (D7). Resolution:

- The *existing* `auto` mode stays exactly as it is.
- The *new* capability (configurable interval, idle backoff, cold-device loading) is what is opt-in,
  via `keep_warm_heartbeat: true`. Off ⇒ today.
- Turning warmth off entirely remains what it is today: `keep_warm_model: "off"` (or `none`/`false`,
  `keepwarm.py:30`), which takes effect on the next tick with no restart (§D6).

If the owner wants the default inverted anyway, that is a **separate, explicit decision** (a D7
change with a migration note), not a side effect of this ticket — Part 3 does not implement it.

### D4. The interval / `keep_alive` relationship

The invariant: `heartbeat_interval_s < parsed(keep_alive)`. If the interval is not shorter than the
window, warmth lapses between pings and the feature is pointless-by-configuration.

- Validation at load time, with a fix message naming both keys.
- A **derived** interval of `keep_alive`/2 always satisfies it for any sane `keep_alive`; the edge
  case is `keep_alive` ≤ `MIN_INTERVAL_S` (30 s), where the derivation is clamped *up* to 30 s
  (`keepwarm.py:87`) and would exceed the window. Today that clamp silently produces a tick that
  pings slower than the model expires.
- Rule: when `keep_warm_heartbeat = true` and `parse_duration_s(keep_alive)` is a positive number
  ≤ 60 s, **reject the config** with "heartbeat needs `keep_alive` > 60s (or turn the heartbeat
  off)". Do **not** clamp silently — a clamp here is exactly the class of bug this packet exists to
  remove.
- `keep_alive` that is negative (load forever, `parse_duration_s` ⇒ `None`) or zero: keep the
  existing skip reason `keep_alive_not_timed` (`keepwarm.py:117`). A forever-resident model needs no
  heartbeat, and the config is not an error.

### D5. Backoff — battery, and idle

- **Battery**: already handled (`_blocked()`, K8). Unchanged, and the heartbeat mode does not
  override it. Note `on_battery` in `LocalTier` (:104) is a *routing* preference and is not evidence
  of the machine's power state — the tick asks `HardwareState` (`:103-106`).
- **Idle**: new. `heartbeat_idle_backoff_s > 0` means: if no routed request has touched the local
  tier for that long, stop pinging and emit one `skipped: idle_backoff` result. Resumption is
  automatic on the next routed request. Implementation detail that matters: the router must record
  a "last local request" timestamp somewhere the daemon can read **without** the tick depending on
  router internals — the honest options are (i) a field the daemon already updates from router
  events, or (ii) a timestamp column in the decisions state store that the tick reads. **Probe P5**
  picks between them; the packet does not assert a mechanism.
- Default `0` = never back off, because "keep my model warm while I think for an hour" is the
  feature's own use case — idle backoff is opt-in, not the default.

### D6. Shutdown and "never resurrects"

- Shutdown: no change needed (K4). The work runs in a daemon thread (`service.py:46`) so a 120 s
  `KEEP_WARM_TIMEOUT_S` (:41) cannot hold exit; `_every` cancels in `finally` (:410-415).
- No resurrection: the task is created unconditionally (:406) and re-reads `live_rules` each tick, so
  `keep_warm_model: off` (or `keep_warm_heartbeat: false`) is honoured on the next tick. The ticket
  adds a **guard test** for this, because "the flag is read from `live_rules` rather than captured at
  construction" is the property that makes it true, and it is easy to break.
- No retry storm: a failed ping returns `error`/`ping_failed` and the tick ends (K9). The next
  attempt is the next scheduled tick. **The packet forbids adding an inner retry loop** and a test
  asserts one HTTP POST per tick on failure.

### D7. Zero cloud traffic, zero routing effect, zero ledger entries

Unchanged from today (K10), and now **frozen by tests** rather than by construction:

- The ping is issued by `KeepWarm` through the `HttpClient` it is handed, to
  `tiers.local.host` only, after the loopback guard (:120-121) and the D13 remote-name refusal
  (:132-134).
- `KeepWarm` must not import the router, quotas or the log writer. A test asserts the tick's
  observable footprint is: at most one `GET /api/ps` and one `POST /api/chat` on the local host,
  and **no** rows added to decisions/cost tables.
- `keep_warm_heartbeat` must not read or write any policy/routing state. It never changes a tier
  order, a wall, or a quota.

### D8. Observability (D18 — one registry, and it already exists)

The dashboard already publishes the keep-warm action and reason (K11). The heartbeat mode adds:

- One INFO log line per *state change*, not per tick:
  `keep-warm: resident model=<id> interval=<s> until=<expires_at>` on first successful ping of a
  model, and `keep-warm: idle backoff` / `keep-warm: resident <id>` when it transitions.
- The same words in the status dict (`service.py:231`) and CLI (`cmd_daemon.py:102-104`): the
  vocabulary comes from `KeepWarmResult.reason` — one source, three readers, no page-side strings.
- `until=<expires_at>` is read from `/api/ps` (whose fields are verified in `ASSUMPTIONS.md`
  `A-OLL-3`). Whether `expires_at` actually *moves forward* after a ping is **P2**, not a fact.

### D9. What this is NOT

- Not a new scheduler, task, thread, or timer — `service.py:305-313` is reused, and this packet
  names it rather than adding one.
- Not a routing change. No tier order, no candidate filter, no wall, no quota, no `max_attempts`.
- Not a second local-model client: it uses the existing `KeepWarm` + `UrllibHttp`.
- Not a way to make a model permanently resident when another model occupies the device — the
  12 GB one-resident rule is deliberate (`:136`) and stays.
- Not a pre-loader for arbitrary models, and not a model download/install path.
- Not a change to the default of `keep_warm_model` (§D3).
- Not a latency guarantee. It removes *load* time from the first request when it can; it does not
  promise a number.

## Part 3 — Normative build

### Slice 1 — Config + validation (no behaviour change)

1. Add `keep_warm_heartbeat: bool = False`, `heartbeat_interval_s: float = 0.0`,
   `heartbeat_idle_backoff_s: float = 0.0` to `LocalTier` (`rules.py:96-111`), with `Field(ge=0)` on
   the two floats.
2. Add the §D4 validation (interval < parsed `keep_alive`; reject `keep_alive` ≤ 60 s when the
   heartbeat is on) and the idle-backoff range check. Each message names the key and the fix.
3. No `keepwarm.py` change. A test asserts the tick's behaviour is identical for a config that omits
   all three keys.

### Slice 2 — The interval knob

1. `KeepWarm.interval_s()` (:82-88): if `keep_warm_heartbeat` and `heartbeat_interval_s > 0`, return
   that value; otherwise keep the existing derivation exactly.
2. `service.keep_warm_interval()` (:299-300) already delegates — no change, and that is the point:
   `_every` re-reads it every loop, so a config edit takes effect without a restart.
3. Test: for an opt-in config, the interval reported equals the configured one; for the default
   config, it equals today's derived value to the float.

### Slice 3 — Idle backoff

1. Establish the timestamp source per §D5 (probe P5 first — do not guess).
2. In `tick()`, after the existing `_blocked()` check: if idle backoff is configured and the last
   local request is older than it, return `KeepWarmResult("skipped", "idle_backoff")`.
3. Emit the transition log line once (state change, not per tick).
4. Tests: backoff triggers on a stale timestamp, resumes when it moves, and never fires when the key
   is `0`.

### Slice 4 — Cold-device loading under the heartbeat flag

Today an explicit `keep_warm_model` already loads when the device is empty (K6) and `auto` cannot
(K5). Under `keep_warm_heartbeat = true`:

1. Keep the rule that a *different* resident model is never evicted (K7) — unchanged.
2. Make K6 explicit in the docstring and covered by a test (it is currently implied by
   `:135-138` and untested), so the loader does not become an accident.
3. If the owner wants `auto` to also load a remembered model, that needs a "last model used" store —
   **out of scope** (§Deferred); the packet does not invent one.

### Slice 5 — Freeze the harmless properties

Tests only, no product code: each `K` row that the owner's brief asserts becomes an assertion.

### Slice 6 — Docs

Document the three keys, the interval/window invariant, that the heartbeat is opt-in and that the
pre-existing tick is not, and the single sentence "this cannot keep a model resident while another
model occupies the device".

### Accept-when

- [ ] With no new keys in the config, the keep-warm tick is unchanged: same interval, same ping
      body, same skip reasons (test 1), and the existing suite passes unmodified.
- [ ] With `keep_warm_heartbeat: true` and `heartbeat_interval_s: 120`, `/api/ps` shows the model
      present with an `expires_at` that is at least `keep_alive` ahead of the last ping, observed
      over a run longer than one `keep_alive` window. (`expires_at` extension itself is P2 — if P2
      says it does not extend, this acceptance item is rewritten to whatever the probe establishes,
      and that is recorded in the ticket.)
- [ ] Measured first-request latency after an idle period longer than `keep_alive`: the
      `decisions.latency_ms` of the first local request with the heartbeat on is materially lower
      than the same request after an idle period with it off, on the same machine and model, and
      both numbers are recorded in the ticket. This is whole-request latency, not TTFT (K14), and
      no first-token claim is made.
- [ ] Exactly one log line per state change: resident, idle backoff, disabled.
- [ ] Zero rows added to any request/cost table, and `count_request` is never called by the tick.
- [ ] Routing, walls and quotas are observably unchanged with the heartbeat on.
- [ ] Ollama stopped mid-run ⇒ the tick reports `ollama_unreachable` once per scheduled tick, no
      faster iteration, and no exception escapes to the daemon log.
- [ ] Daemon stop returns promptly (< 2 s) with the heartbeat on and a ping in flight (daemon thread,
      `service.py:46`).
- [ ] Turning the heartbeat off in the live rules takes effect on the next tick without a restart,
      and it does not come back on its own.

### Deferred / out of scope

- Remembering the last-used model so `auto` can reload it (§D5/Slice 4.3) — needs a small state
  store; separate ticket.
- Any change to the default of `keep_warm_model` (§D3) — owner decision, D7 change, migration note.
- Pre-warming before a predicted request (needs a predictor; nothing here predicts).
- Multi-model residency or VRAM budgeting changes (that is the hardware/fit maths, HDW-138).
- A first-token/TTFT metric (K14) — would be a new measurement in the executor, not a heartbeat job.
- Extending the heartbeat to the free-cloud tiers ("keep a provider warm") — different domain,
  different constraints, no `keep_alive` equivalent.
- Install/download of a missing model.
