**Build:**
- A verification spike like HDW-002, on a real machine with real hosts and a real Ollama model. Record every result in `docs/ASSUMPTIONS.md` with the host version and date; every failure becomes a follow-up in the report.
- **Daemon lifetime (FU-202-1):** start the shim from VS Code, Claude Desktop and Cursor (whichever are installed), close the first IDE, and check the daemon still answers. If it dies, say which Job Object rule applies and propose the fix (scheduled task, service or `cmd /c start`).
- **Shim working folder (FU-204-3):** which folder each host starts the shim in, and whether it sends roots.
- **Real model through the shim:** `headwaters_do` end to end, a job with progress, `headwaters_more` (list, call, list again), result links after a daemon restart, job status and result tools (FU-204-6, FU-204-9, FU-205-10, FU-206-6, FU-206-7).
- **Real thinking model:** `headwaters_think` with a model that takes named levels (gpt-oss) and one that does not think (FU-205-4, FU-140-2); keep-warm against a real Ollama (FU-201-8).
- **Estimates:** measure real cold-load seconds, output tokens and cloud tokens per second against the numbers in `headwaters/mcp/tools/context.py` (FU-206-3); HDW-704 tunes them later.
- Add `-m live` tests wherever a check can be repeated.
**Accept when:** the report holds a table of host x check x result; every failure has a follow-up; ASSUMPTIONS rows exist with versions and dates; the daemon-lifetime question is answered for each installed host.

## Part 3: Follow-ups and evidence

Source: follow-ups read by the triage session of 2026-11-01 (`docs/FOLLOWUPS.md`, `docs/reports/`).

| FU id | From | Kind | Summary |
| --- | --- | --- | --- |
| FU-202-1 | HDW-202 | bug | ``headwaters/core/daemon_control.py`, HDW-203 / HDW-206`: Under the SDK's stdio client on Windows the shim sits in a kill-on-close Job Object that does not allow breakaway, so a daemon the shim starts can still be reaped when that client disconnects (seen with `mcp.Client`). The live tests therefore check the daemon while connected and start it themselves where it must outlive a client. Real hosts (VS Code, Claude Desktop, Cursor) may or may not use such a job; if they do, the first use would start a daemon that dies with the first IDE. Check on a real host, then consider launching through a scheduled task, a service or `cmd /c start`. |
| FU-204-3 | HDW-204 | risk | `headwaters/mcp/shim.py`: The boundary is the shim's `os.getcwd()`. A host that starts the shim from its install folder, not the project, would see `no_workspace` or a wrong folder. Check real hosts (VS Code, Cursor, Claude Desktop) and use the roots capability or an installer-written root where needed. `META_ROOTS` is read by the tools but the shim does not send it yet. |
| FU-204-6 | HDW-204 | gap | `headwaters/mcp/tools/store.py`: Results live only in daemon memory: a daemon restart makes every `result_uri` answer "unknown or expired". If hosts keep links across restarts, store the detail in SQLite (still without task or file text). |
| FU-204-9 | HDW-204 | test | `tests/test_daemon_live.py`: No live test calls a tool end to end through the shim with a real model. A `-m live` test with a real Ollama model would cover `headwaters_do`. |
| FU-205-4 | HDW-205 | risk | `headwaters/mcp/tools/frontdoor_more.py`: `headwaters_think` sends `think: true`. Ollama's docs say some models (gpt-oss) take named levels and an unsupported name falls back to the model default; not tested against a real model.
