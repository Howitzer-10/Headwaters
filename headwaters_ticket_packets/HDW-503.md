#### Keys section (supersedes the read-only doctrine, for this page only)

The status page today has no forms, no inputs, no scripts and no clickable controls, because a
loopback HTML page that accepts writes is a CSRF surface (Part 3 records the doctrine this
replaces). That changes here, for exactly one section. Everything else on the page stays
read-only, and the page still works with JavaScript disabled: the keys section is plain HTML
forms plus one `<details>` per provider.

- **One row per provider and alias, read from `KeyStore.entries()`** — never a hard-coded
  provider list. Each `KeyInfo` already carries `alias`, `provider`, `env_var`, `source`
  (`"credential store"` / `"environment"` / `"not set"`) and `masked`. Each row shows provider,
  alias, source, masked value, last test status and time, and the actions
  **Set / Replace / Remove / Test**.
- **Grouped by provider and expandable**: one `<details>` per provider whose `<summary>` shows
  the provider, its source and its status; opening it shows that provider's aliases with their
  own source and the per-alias actions. (An alias whose source is `environment` and another in
  the credential store are two rows under the same provider; say which is which.)
- **Add key form** at the top of the section: alias (defaults to the provider name), provider
  (`<select>`), secret (`<input type="password" autocomplete="off">`), submit. The secret is
  **never echoed back**: after any outcome the field comes back empty, and no response body,
  redirect target, log line or error message contains the value or any part of it.
- **The provider list grows with no code change.** It is the key store's own provider list:
  `STANDARD_ENV` (`anthropic`, `openai`, `openrouter`) plus every
  `rules.models.openai_compatible[*].name` — which is exactly what `KeyStore._default_records()`
  assembles. That method is private: add a small public accessor (e.g.
  `KeyStore.providers() -> list[str]`) and have the page read that, so a provider registered by
  the provider registry (HDW-514) appears in the dashboard with no change here.
- **Honest status; never a green tick for an absent key.** A provider with no key reads
  **not set**, and the row says in words what that costs in this install: that provider cannot
  be routed to, so requests fall back to free cloud (`:free`) and local models only — and if
  that makes paid scope unusable, say so plainly. Green means "a key is present **and** the last
  test passed"; a key that has never been tested reads **not tested**; a `blocked` test result
  (Private lock, airplane mode, local scope) is shown as blocked with its reason, not as a
  failure.
- **Remove tells the truth.** Removing an alias whose source is `environment` cannot unset the
  variable, so the page must say the key will come back from `<ENV_VAR>` until the variable is
  removed from the environment. Never show it gone when it is not.
- **Deep links.** `?section=keys` renders the keys section **first** (server-side reordering —
  there is no script to scroll with), the section carries `id="keys"`, and each provider
  `<details>` carries `id="keys-<provider>"` (provider names are already restricted to
  `[A-Za-z0-9_.-]+`; escape it as HTML anyway). So the tray opens
  `/?section=keys#keys-<provider>`. **Fragments never reach the server**: only `?section=` is
  read server-side, and `#keys`, `#keys-<provider>` are plain HTML anchors.

#### Keys write API (every line here is an accept-when)

Routes on the **dashboard** app only (`build_status_page_app` in `headwaters/gateway/server.py`),
which the daemon already binds to `127.0.0.1`:

| Method | Path | Effect |
| --- | --- | --- |
| POST | `/keys/set` | store the secret for an alias/provider (`KeyStore.save`) |
| POST | `/keys/remove` | delete the stored secret (`KeyStore.remove`) |
| POST | `/keys/test` | run the same check as `headwaters keys test` and record the result |

The CSRF token **is** the authentication for these routes: a browser has no bearer token, so
these are not on the token-guarded `/v1/*` app (`GuardedApp`) and must not be. That is why items
2–4 are mandatory, not defence in depth:

1. **Loopback port only.** Serve on the dashboard socket the daemon already bound to
   `127.0.0.1` (`pipe_ports` / `bind_first_free`). Do not open a second listener, do not
   re-bind, and do not trust `rules.dashboard.port` as the truth: `bind_first_free` may have
   picked another port, so the expected port is `DaemonInfo.ports.dashboard`.
2. **CSRF token, one per daemon start**: `secrets.token_urlsafe(32)`, held in daemon memory only
   (**not** in `daemon.json`, which any local process can read), rendered as a hidden `csrf`
   field in every write form. Every POST must carry it; missing or wrong → **403** and **nothing
   is written** (compare with `hmac.compare_digest`).
3. **`Host` must be loopback *and* carry the dashboard port** — exactly `127.0.0.1:<port>`,
   `localhost:<port>` or `[::1]:<port>`, else **403**. Note the existing guard differs:
   `LoopbackOnlyApp._refusal` answers **421 `bad_host`** and `is_loopback_authority` checks the
   hostname only, never the port. Add the port-aware check for the write paths without changing
   the read path's 421 (the existing test asserts it) and without writing a second, weaker copy
   of the guard.
4. **`Origin`/`Referer`, if present, must equal the dashboard origin** (`http://127.0.0.1:<port>`
   or `http://localhost:<port>`), else **403**. Prefer `Origin`; fall back to `Referer`; both
   absent is allowed (curl and the tray send neither).
5. **Form-encoded bodies only**: `Content-Type: application/x-www-form-urlencoded`, else
   **415**; cap the body (a few KiB) and reject anything larger with **413**. No multipart, no
   JSON.
6. **No CORS headers at all** — no `Access-Control-Allow-*` on any response, no preflight route;
   `OPTIONS` on these paths is **405**.
7. **The secret travels in the request body only**: never in the path, never in a query string,
   never in a redirect target. Never log it — log the alias and the outcome only.
8. **POST-redirect-GET on success**: **303** to `/?section=keys#keys-<provider>`. A failure is
   not redirected into a 200 page that looks like success: re-render with its own status code
   and an error line.
9. **Failures reuse the existing redaction.** `KeyStoreError` messages carry no value; apply the
   same redaction the CLI uses. A test must assert the secret appears in no response body and no
   error string.
10. Only `GET` and `POST` are routed on these paths; any other method → **405**.

**Last test status and time must be persisted**, because nothing records it today: `check_keys`
returns a `PingResult` and it is discarded. Add a small table through the existing `core.state`
migration path (`key_tests(alias PRIMARY KEY, ts REAL, status TEXT, detail TEXT)`, beside
`state_limits.py` / `state_decisions.py`), written by the daemon after a test and read by both
the page and `headwaters keys test`, so the CLI and the dashboard never disagree and never keep
two copies of the ping logic. `detail` holds the redacted `PingResult.detail` (host, HTTP code),
never a key.

#### Tests to add, update, and not delete

- 403 paths, one test each: missing token, wrong token, foreign `Host`, foreign `Origin`; plus
  415 for a JSON body and 405 for `OPTIONS`.
- set → the page lists the alias, masked (`mask()` output) with source `credential store`.
- remove → the alias is gone, or reads `environment` with the "returns from `<VAR>`" note.
- test → a result is recorded and rendered with its status and time (HTTP mocked; no network).
- the rendered page and every error string contain neither the secret nor a prefix of it.
- **Update, do not delete, the existing read-only assertions.** `tests/test_status_page.py`
  asserts the page contains none of `<form`, `<input`, `<button`, `<script`, `onclick` (around
  line 103). Keep the test and rewrite it: reads stay free of `<script` and `onclick`, and the
  only forms are the keys forms, each carrying a `csrf` field.
- **Update the doctrine in `headwaters/control/status_page.py` in the same implementation
  commit** (its module docstring, quoted in Part 3). Keep the reasoning, change the conclusion.

#### Where the code goes (do not fight the linter)

Contracts from `.importlinter`, not style preferences:

- **`headwaters.core` must not import** `headwaters.features`, `gateway`, `mcp`, `daemon`,
  `control`, `installer`, `packaging` or `cli` (`core-is-a-leaf`). Data lives in core
  (`core.keys`, the `key_tests` state module); nothing else does.
- **Only `headwaters.gateway` may import `fastapi`, `starlette` or `uvicorn`**
  (`web-framework-only-in-gateway`), and `headwaters.features` may not.
- **The daemon is the composition root** (`daemon-is-a-root`): nothing imports
  `headwaters.daemon`. It wires the key store, the page renderer and the servers.
- **So the page model stays in `headwaters/control/status_page.py`** — a control module that
  imports core only, holds no web framework, returns pure data from `build_page` and pure text
  from `render_html`. Extend it there: a `PageKey` dataclass, a `keys` field on `StatusPage`, a
  keys block in `render_html`, `section`/`anchor` arguments. **The gateway** parses the request
  and calls the renderer the daemon hands it — widen `build_status_page_app(*, render)` from
  `Callable[[], str]` to receive the request URL so `?section=` reaches the renderer. The
  gateway decides nothing; the renderer does not know about sockets.
- **No ★ feature module may serve HTTP.** `headwaters/features/` is where the ★ flag lives, and
  a feature flag is registry metadata only (`core.features`). There is no `features/dashboard`
  HTTP server and this ticket must not create one.

#### Provider identity (binding, D18; every line here is an accept-when)

Decision D18 in `docs/DECISIONS.md`: the CLI, this page and the tray (HDW-504) all use **one**
set of plain, lowercase provider names, and a person never sees an underlying environment
variable name. This section **overrides** anything above that says otherwise: the `env_var`
field of `KeyInfo` and the `<ENV_VAR>` / `<VAR>` wording in "Remove tells the truth" and in the
tests are internal-only and are never rendered.

- **Names come from the shared registry, never from this page.** Provider names are rendered
  from the registry owned by HDW-514 (`headwaters/core/keys.py`, read through the public
  `KeyStore.providers()` this ticket already adds). The page holds no provider list, no label
  table and no display-name mapping of its own, and it does not rename a provider for
  presentation: the name on the page is the name `headwaters keys set <name>` takes
  (`anthropic`, `openai`, `openrouter`, `nvidia`, `huggingface`, `mistral`, `pollinations`,
  `opencode`, `kilo`, and keyless `ollama`).
- **Never display an environment variable name.** Not in a row, a `<summary>`, a tooltip, an
  attribute a person can read, an error line, a "Remove" note or a placeholder. For an
  `environment` source, say in words that the key comes from the system environment and will
  keep coming back until it is removed there, without naming the variable. The form's provider
  `<select>` shows canonical names only and its values are canonical ids.
- **Never display a key prefix for a key the person did not just type.** Today's `mask()`
  returns the first four and last four characters, and the first four identify the vendor, so
  the page must **not** render `KeyInfo.masked` as it stands. A saved key is shown as saved,
  with at most its last four characters (a prefix-free mask added beside `mask()` in
  `core.keys`; `mask()` itself and the CLI are unchanged by this ticket). This supersedes
  "masked value" in the row definition and the set-test above ("masked (`mask()` output)").
  No other hint derived from a key is rendered either, such as "starts with `nvapi-`". The
  secret field still comes back empty after any outcome (see "Add key form").
- **Never display an internal alias mapping.** The page does not show how a name maps to an
  environment variable, a litellm provider string, a base URL or a registry field. An alias
  row shows its alias; it does not show what the alias resolves to internally.
- **Every provider row shows the same four facts in plain words:** the plain provider name;
  whether a key is **required** (keyless providers such as `ollama` and `pollinations` say so
  rather than showing a "not set" warning); whether a key is **saved** (the honest source from
  the "Honest status" rule); and its **validation result** (`ok`, `unauthorized`, `http_error`,
  `unreachable`, `blocked`, `unsupported`, or **not tested**, as already specified). The
  "requires a key" fact is read from the registry, not guessed from the provider name.
- **A provider registered in HDW-514 appears here with no change in this ticket's code**, under
  its canonical name.
- **Test: no env-var name in rendered text.** Build the page from a key store whose registry
  has every shipped provider (and one fake entry added in the test), with the environment
  variables set for some and unset for others. Collect every env-var name the registry
  contains (`HF_TOKEN`, `NVIDIA_API_KEY` and the rest, read from the registry, not retyped) and
  assert that **no rendered page text** matches any of them, case-insensitively, across the
  full page and every error and note string, including the `environment`-source "Remove"
  note. A second assertion checks the rendered provider names equal `KeyStore.providers()`
  exactly, so a hard-coded list or a renamed label fails the test.

### Normative: the read-only doctrine this ticket supersedes

`headwaters/control/status_page.py` (HDW-404) currently opens with, verbatim:

> """The read-only status page (HDW-404): the same facts as ``headwaters status``, as HTML.
>
> Core module: no web framework and no daemon import (D14). The daemon builds a page from its live
> rules, project rule, feature registry and the shared SQLite state; ``headwaters.gateway`` serves
> it on the loopback dashboard port. ``build_page`` is pure data (so a test can build one from real
> walls and real decision rows), ``render_html`` is pure text.
>
> Read-only means no editing controls at all: buttons, forms and switches belong to the ★ dashboard
> (HDW-503). Nothing here has a secret in it: walls, decisions and quota rows are metadata.
> """

That paragraph is the *reason* the page was safe, and the reason is still right: a loopback HTML
page that accepts writes is a CSRF surface. What changes is the conclusion, not the argument.
Rewrite it in the same commit as the code so the next reader learns why the four checks exist
instead of why there are no writes:

- the page is no longer read-only: it has exactly three writes (`/keys/set`, `/keys/remove`,
  `/keys/test`) and they exist only behind the CSRF token, the `Host`-with-port check, the
  `Origin`/`Referer` check and a form-encoded body;
- everything else on the page is still read-only, and there is still no JavaScript;
- **"Nothing here has a secret in it" stays true and stays in the docstring**: the most the page
  ever shows is `KeyStore.mask()` output, and that promise is what the no-secret test asserts.

`tests/test_status_page.py` asserts the same doctrine from the outside, over `("<form", "<input",
"<button", "<script", "onclick")` (around line 103). **Update that test; do not delete it.** The
assertions about `<script` and `onclick` survive unchanged; the ones about `<form`/`<input`/
`<button` become "the only forms on the page are the keys forms, and every one of them carries a
`csrf` field". A deleted test would remove the guard that keeps the rest of the page read-only.

### Normative: measured facts in the code this ticket touches

Verified in the repo at packet-writing time; re-verify before coding, and if the code has moved,
follow the code and note the deviation.

- `headwaters/core/keys.py` — `STANDARD_ENV = {"anthropic", "openai", "openrouter"}` to env-var
  names; `KeyInfo(alias, provider, env_var, source, masked)` with `source` in
  `{"credential store", "environment", "not set"}`; `KeyStore.entries()`, `.aliases()`,
  `.save(...)`, `.remove(alias) -> bool`, `.secret(alias)`; `mask()` is the only masking
  helper, so use it rather than formatting a mask yourself. `_default_records()` (private)
  merges `STANDARD_ENV` with every `rules.models.openai_compatible[*]` endpoint — that merge is
  the provider list the page needs, hence the public accessor.
- `headwaters/control/keys.py` — `target_for(provider, ...)` maps openrouter → `/key`, anthropic
  and openai → `/v1/models`, each endpoint → `{base_url}/models`, and returns `None` →
  `unsupported`; `check_keys(store, rules, http=..., aliases=...)` returns
  `PingResult(alias, provider, status, detail)` with `status` in `ok`, `unauthorized`,
  `http_error`, `unreachable`, `blocked`, `unsupported`. The dashboard's **Test** action calls
  this, not a copy of it.
- `headwaters/gateway/server.py` — `STATUS_PAGE_PATHS = ("/", "/index.html")`;
  `build_status_page_app(*, render: Callable[[], str])` wraps `LoopbackOnlyApp(Starlette(...))`
  and answers `PAGE_FAILED` with 500 on a render error; `LoopbackOnlyApp._refusal` returns
  `421 bad_host` / `403 bad_origin`; `is_loopback_authority` checks the hostname only and
  `_origin_ok` likewise does not compare the port. `GuardedApp` (bearer token) guards the
  `/v1/*` API app, which is a different app on a different port.
- `headwaters/daemon/service.py` — `DashboardContext.dashboard_page` renders the page for the
  dashboard socket; `pipe_ports` / `bind_first_free` choose the ports, so the live dashboard
  port is `DaemonInfo.ports.dashboard`, not necessarily `rules.dashboard.port` (default 4001).
- `headwaters/core/rules.py` — `DashboardRules(enabled, port=4001)`; `OpenAICompatEndpoint` is
  what supplies the extra providers.
- `headwaters/features/` — currently only `__init__.py`: there is no feature module to extend,
  and this ticket does not create one (see the placement rules in Part 2).
