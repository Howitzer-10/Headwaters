### 1. The owner's ask, restated precisely

Today the router's answer to "is this answer any good?" is **report, never act**: a failed check
sets `status: verify_failed` on the log entry and hands the answer back to the host. There is one
narrow exception — an **upward** retry to a *stronger* model, and it only fires when verification
was mandatory. Nothing today ever hands work **down** to a cheaper or local model.

The requested capability is the downward hand-off. Written as a contract:

> When the answer from a stronger tier fails a check we can actually run, retry **once** on a
> weaker tier (ultimately local), return that answer instead, and label the whole exchange
> honestly — including when the weak answer also fails.

The hard part is **not** the hand-off. It is the **pass/fail signal**: our hosts are third-party
clients (Cline, OpenCode, Claude Desktop, VS Code) and none of them tells us whether an answer was
good. Part 2 §D1 is therefore the longest section of this packet, and it deliberately spends more
words on *what we may claim* than on the mechanism.

## Part 2 — Design

### D1. The signal contract — provenance of the pass/fail

Everything in this ticket is downstream of one question: **what event are we allowed to treat as
"the draft was not good enough"?** Four candidates, with their real limits.

| # | Candidate signal | Observable through our proxy today? | Real limits | Phase |
|---|---|---|---|---|
| a | Host retries / regenerates, seen as a repeat request | **Partly.** A regenerate usually arrives as a *new* request. We can only match it if `x-session-id` is stable and the prior answer was routed. | Cannot distinguish "regenerate because bad" from "user edited the prompt and asked again". Same-session repeats are also normal conversation. | later |
| b | Host runs a check itself (lint, test, compiler) and tells us | **Not today.** Nothing in our five endpoints accepts a verdict (`openai_routes.py:83-113`). The host *can* call `headwaters_check` (`frontdoor.py:65-90`), but that is the host asking us, not the host reporting. | Requires host configuration we do not control; this is the highest-fidelity signal and the furthest out of reach. | later (needs a host capability we do not have) |
| c | A cheap automated check the proxy runs on the answer | **Yes, and it already exists.** `run_verifiers` + `BasicVerifier` (`router_verify.py:63-82`, `verify_basic.py:88-121`). | Only catches *structural* faults: empty/truncated output, invalid JSON against a supplied schema, malformed tool-call arguments, no checks that ran (F11). It says **nothing** about being correct, helpful or well-written. | **phase 1** |
| d | Explicit user feedback (thumbs) | **No.** No endpoint, no UI contract, no storage. | Highest intent, lowest volume, needs UI in hosts we do not own. | later |

**Phase-1 default: (c), and only (c).** Reasons, in order:

1. It is the only signal whose provenance we control end to end — the check runs in our process on
   our own output, so a `fail` is *our* observation, not a host's opinion we cannot audit.
2. It is already implemented, type-safe, and honest — including the F11 rule that a run which
   checked nothing is **not** a pass (`router_verify.py:81-82`). That single rule is what keeps us
   out of the "we verified it" lie.
3. (a) is the tempting one and it is a trap for phase 1: with `session_key` derived from a prompt
   hash (`router_session.py:65-82`) a regenerate after an *edit* looks identical to a regenerate
   after a *complaint*. Acting on it would let a user's ordinary follow-up silently downgrade their
   next answer to a local model.

**(c) is deliberately narrower than the owner's ask.** Under (c) we detect *malformed drafts*, not
*unsatisfying drafts*. This packet states that plainly rather than quietly widening (c) until it
looks like quality judgement. Widening (c) to "does this answer look right" is a verifier-design
problem (later: a judge model, ★ HDW-901 territory) and is out of scope here (§D9).

### D2. The capability — a downward hand-off, not a new verifier, not a new plugin

**Name: `verify_cascade`.** Deliberately *not* "escalate": the existing word already means "go up"
(§D3), and a report that says "escalated" while spending *less* money would corrupt the ★ ledger's
savings reading.

Contract:

1. Fires only when `VerifyOutcome.failed` is true — i.e. `ran and passed is False`
   (`router_types.py:129`-ish property). **Never** on `passed is None` (nothing established) and
   never on `skipped`/`unchecked` (§D7).
2. Retries **exactly once**, on a candidate from a *strictly lower* tier than the model that
   drafted. "Lower" is defined by HDW-516's ordering, not by task score.
3. If the second answer passes, return it and say so. If it fails, return it **flagged** — we do not
   loop downward through every tier.
4. When the capability is off, behaviour is byte-identical to today (F5).

### D3. Where it lives

Today: `_escalate` is called at `router.py:176` and is structurally up-only — the F10 filter at
`:543` (`stronger_than=decision.breakdown.quality`) is the encoding of "go up, never sideways", and
`:474` explains why (tool-quality regressions on downward moves).

The downward move therefore **cannot** reuse `_escalate` without breaking F10, and must not be
smuggled in as an `EscalationPlugin` — the plugin protocol only receives `(attempt, problems)`
(`plugins.py:89-95`), so a plugin could not express "go to a lower tier" without the router
lowering F10 for plugins in general. That would weaken HDW-154 for every plugin.

Design: a **separate step, `_cascade`, called after `_escalate` returns `None` at :176**, so the
upward path is tried first and the downward path is the fallback — never the other way round (an
upward retry is a better answer; a downward one is a cheaper answer of last resort).

```
attempt loop (router.py:150-200)
  ├─ call model
  ├─ verify                      (unchanged)
  ├─ _escalate(...)  → decision?  (unchanged; F10 enforces "up")
  └─ _cascade(...)   → decision?  (new; only if verify_cascade enabled)
        ├─ guard: verify.failed and not verify.passed       (D2.1)
        ├─ guard: rules.router.verify_cascade               (opt-in)
        ├─ guard: run.cascades >= 1                          (one hop, D2.2)
        ├─ guard: len(run.attempts) < max_attempts           (F10, rules.py:210)
        ├─ guard: not pinned / pin_strict                    (D5)
        ├─ redecide with descending order from HDW-516, target tier strictly lower
        └─ run.excluded.add(failed model); run.cascades += 1
```

`_cascade` mirrors `_escalate`'s honesty: on `RouteFailed` (no lower candidate available) it
**discards** the exclusion and returns `None`, handing back the flagged draft rather than pretending
it did not happen (`router.py:541-543` is the model to copy).

### D4. Interaction with HDW-516

- 517 **consumes** 516's ordering. The target set is "candidates strictly lower than the drafter in
  the configured direction".
- If 516 is not landed, 517 must not guess an order from `interleave_tiers` — the round-robin
  guarantees a tier repeat before a full descent, which is the opposite of what a cascade wants.
  Hence the hard dependency.
- 516's default (unchanged behaviour) means a deployment that enables `verify_cascade` but leaves
  the ordering at round-robin gets a **documented, tested refusal at config validation**, not a
  mysterious no-op. Cascade requires `preference` to be descending (either direction).
- Degenerate case: `preference = local-only` + `verify_cascade` is contradictory (nothing lower to
  descend to) and is rejected the same way.

### D5. Interactions that must be stated

| With | Rule |
|---|---|
| `pin` (a model was named) | A pin is a user instruction, not a suggestion: **the cascade never fires** on a pinned request. Pinned output that fails verification is reported, exactly as today (F5). |
| `pin_strict` | Never fails over (as today, `router.py:410/:455`); cascade included. |
| Walls / quotas | The lower target must be *usable*. An exhausted local tier is filtered by `filters.py:99-100` before the ladder, so the cascade sees it as absent. A wall means **no descent** — and never a silent downgrade to something the user excluded (D19). |
| Failure memory (HDW-513) | `run.excluded` already holds failed models (`:539`); the cascade adds the drafter and inherits the never-re-pick rule. It does **not** write a `FailureMemory` record for "failed verification" — that memory is about *transport/provider* failures, and a malformed answer is a different class of fact (see §D9). |
| F16 | An answer that failed verification is never pinned (`:581-583`); this stays true for both attempts. |
| Streaming | Does not cascade (`router.py:22`). Inherited limitation, tested so it cannot silently change. |

### D6. Config surface

New keys, all under `rules.router`, all default-off so D7 (no silent behaviour change) holds:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `verify_cascade` | bool | `false` | Opt in to the downward hand-off |
| `verify_cascade_model` | str | `""` | Empty = choose the target by 516's descending order; set = that model or nothing (no fallback to "some other lower model") |
| `verify_cascade_tasks` | list[str] | `["code"]` | Which task classes may cascade — mirrors `FloorsRules.verifiable_tasks` (`rules.py:128`) rather than inventing a second vocabulary; validation rejects a value that is not one of those tasks |

Validation, all at load time with a fix message (never a silent clamp):

- `verify_cascade = true` with ordering not descending → reject (D4).
- `verify_cascade = true` with `verify = "off"` → **accept but force the gate** for the tasks in
  `verify_cascade_tasks`. Rationale: a cascade with no gate can never fire, and silently never
  firing is worse than a wider gate. This is a deliberate, documented exception to `verify = "off"`
  and gets its own test, because `wants_verify` (`router_verify.py:21-25`) already contains the same
  principle (`required` beats `off`).
- `verify_cascade_model` set to a model not in a lower tier than the configured top → reject.

### D7. Honesty rules (non-negotiable)

1. **No quality score.** We will not emit, store or display a number purporting to measure answer
   quality. `VerifyOutcome` has no such field (F3); neither `Verification`
   (`mcp/tools/verify.py:30-44`) will grow one. What we emit is a *check result*, not a grade.
2. **Nothing established is not a pass.** `passed is None` never triggers a cascade and never reads
   as success (F4, F2). A run where every check was skipped is `skipped`.
3. **Never claim "verified".** The dashboard/CLI wording is "checks passed" / "checks failed" /
   "not checked". A cascaded answer that passed gets "checks passed (after cascade)".
4. **Report the real numbers.** The acceptance run publishes the observed cascade rate and its
   pass rate even if unflattering. A low cascade rate means the gate does not catch much — that is a
   finding, and it is the honest input to the phase-2 decision.

### D8. Where the strategy is expressed (D18 — one registry)

Same rule as HDW-516: the *name* of the capability and the words for its outcomes live in the
one provider/policy-name registry the CLI, dashboard and tray already read. Concretely:

- Config key names come from `rules.py` (`RouterRules`) — one definition, validated once.
- Outcome vocabulary (`pass`/`fail`/`skipped`/`unchecked`, plus `cascaded`) is defined once next to
  `VerifyOutcome.status` (`router_types.py:133+`) and reused by `cli/pick_report.py`, the dashboard
  and the tray. No page invents its own words.
- `LogEntry` gains `cascade_to: str | None` (written in `_entry`, `router.py:598-625`) —
  **separate from `escalated_to`** (:577/:624), because `escalated_to` means "spent more" and the
  ★ ledger reads it as such. Two directions in one field would make the savings figure lie.
- Events: `_emit(run, "cascading", decision, "verify_failed")` mirrors `"escalating"` (:547).

### D9. What this is NOT

- Not a verifier. No new `VerifierPlugin`, no judge model, no scoring algorithm.
- Not a change to `EscalationPlugin` or to F10 (upward-only stays true for escalation).
- Not a router, a ladder, or an ordering change — that is 516.
- Not tier membership or scope: the set of allowed tiers is untouched.
- Not a host integration. We do not require Cline/OpenCode/Claude Desktop/VS Code to change anything
  for phase 1 to work.
- Not a failure-memory change: a malformed answer is not a provider outage and must not quarantine
  a provider.
- Not a streaming feature.

### Accept-when

- [ ] With `verify_cascade = false` (the default) the full existing suite passes **unmodified**, and
      a failing gate still returns `status: verify_failed` with the draft.
- [ ] With `verify_cascade = true` and a descending order: a structurally invalid cloud draft (e.g.
      invalid JSON against a supplied schema) produces a second attempt on a strictly lower-tier
      model, exactly one, and the final `LogEntry` has `cascade_to` set and `escalated_to` null.
- [ ] If that second answer also fails, exactly two attempts are logged, `status: verify_failed`
      carries, and the answer is returned flagged — no third model.
- [ ] An upward escalation, when one is available, is used **instead of** a cascade.
- [ ] A pinned request never cascades (pin and `pin_strict` both covered).
- [ ] An exhausted lower tier yields no cascade and no wall bypass.
- [ ] `verify = "off"` + cascade ⇒ the gate demonstrably ran (`ran is True`).
- [ ] The acceptance run publishes: number of gated requests, number that failed, number that
      cascaded, and the cascade pass rate — as counts and rates, with no quality score anywhere.
- [ ] `ruff`/`mypy` clean if the repo runs them for the touched modules (implementer's call — not run
      in this packet's authoring).

### Deferred / out of scope

- (a) regenerate-detection, (b) host-reported verdicts, (d) thumbs — each needs either a host
  capability or a UI we do not own; phase 2 at the earliest, after phase-1 numbers exist.
