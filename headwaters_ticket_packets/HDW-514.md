## Part 2: Ticket

### HDW-514 · Free cloud providers
**Model** Sonnet · **Effort** Large · **Depends** 103, 105, 401, 503 · **Class** core, no ★ · **Refs** v3 §4.2, v3 §6, v3 §14, v3.3 §A, v3.3 §F

**Goal:** as many free cloud providers as possible, available to routing, each behind the same
source interface, each with a key the user supplies in the dashboard — and each verified against
its own current official documentation before a line of code is written for it.

This is **additive**. OpenRouter `:free` and the OpenCode free path keep working exactly as they
do today; nothing in this ticket changes them, and a shipped provider must not make either worse.

#### The verification protocol (applies to every slice below, no exceptions)

The Context Pack rule stands: *verify any external API against current official docs before
coding it; record in docs/ASSUMPTIONS.md; isolate behind an interface.* Concretely, per provider:

1. Read the provider's **current official** documentation (vendor docs, not blog posts, not
   aggregators, not another project's code — the clean-room rule still applies).
2. Confirm, and write down: the **base URL**, the **auth style** (bearer? header name? query
   param?), the **metadata/validation endpoint** (the thing `headwaters keys test` can call to
   prove a key works without spending a completion), the **model-listing endpoint** and response
   shape, and the **free-tier** facts (what is free, what the limits are, whether a key is
   required at all).
3. Record each confirmed fact as a row in **docs/SDK_FACTS.md** under a new
   `## Cloud provider APIs (HDW-514)` table with the existing four columns
   (`Fact | Verified by | Version | Ticket`, ticket = `HDW-514`), and add an **docs/ASSUMPTIONS.md**
   row that points at that SDK_FACTS.md section rather than repeating it.
4. Only then write the registry entry and the tests.

**Do not invent an endpoint URL, a header name, an environment variable name or a model slug.**
If the docs do not state it, it does not go in the code; the packet's guesses are labelled as
guesses and are not to be trusted (the tables below deliberately name **no** URLs). If a fact
cannot be verified, the slice is **not implemented** — instead it gets an ASSUMPTIONS row saying
what is unknown and a follow-up (FU) line in `docs/reports/HDW-514.md` naming what would unblock
it.

#### Slice A · Provider registration becomes data, not code (do this first)

One registry entry per provider, in **data**, consumed by every layer — after this, adding a
provider is a data change plus a test:

| Field | Meaning |
| --- | --- |
| `name` | the provider key used by routing, `headwaters keys set <name>`, `KeyStore` and the dashboard |
| `env_var` | the environment variable that can supply the key (e.g. the `STANDARD_ENV` style) |
| `base_url` | the API root the executor and discovery call |
| `auth_style` | how the credential travels (bearer header, `x-api-key`, etc.) |
| `metadata_endpoint` | the validation/metadata call `headwaters keys test` makes (may be `None` → `unsupported`) |
| `models_endpoint` | the model-listing call discovery makes |
| `tier` | `free_cloud` or `paid` — see "Free/paid classification" below |
| `free_notes` | the documented free-tier limits, for the wall/limit layer |

Placement: the data belongs with the catalog ("curated, signed, updatable" — the seed catalog
already carries an `endpoints` section that holds the OpenRouter base URL), loaded by a new
`headwaters/core/providers.py`. `rules.yaml` may override a base URL for a provider, but **no
provider may require editing rules.yaml to work**.

Consumers to convert, all of which today have provider-specific code or a hard-coded list:

- **`headwaters/core/keys.py`** — `STANDARD_ENV` (`anthropic`, `openai`, `openrouter` →
  `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`) stops being the only source of
  known providers: the registry contributes its entries, so `KeyStore.entries()` lists them and
  `headwaters keys set <name>` works with no rules.yaml edit. Keep `STANDARD_ENV` working —
  existing aliases, saved keys and tests must not break.
- **`headwaters/control/keys.py`** — `target_for(...)` currently branches per provider
  (openrouter → `/key`, anthropic/openai → `/v1/models`, each `openai_compatible` endpoint →
  `{base_url}/models`, otherwise `unsupported`) and `check_keys(...)` returns
  `PingResult(alias, provider, status, detail)`. Drive both from `metadata_endpoint` +
  `auth_style` so a new provider needs no `if` in this file, and keep the existing status
  vocabulary (`ok`, `unauthorized`, `http_error`, `unreachable`, `blocked`, `unsupported`).
- **`headwaters/core/catalog/discovery.py`** — the sources are `ollama`, `opencode`,
  `openrouter` and `openai_compatible:{endpoint.name}`. Add one generic registry source
  (`provider:{name}`) driven by `models_endpoint`, without touching the existing four;
  `network_block(rules)` (airplane, local-only lock) must block the new sources exactly as it
  blocks OpenRouter today, and a provider outage must be a warning, never a deletion of the
  models already known (same rule as Ollama).
- **the executor** — auth style and base URL come from the registry (still called through
  litellm, per the Context Pack); a provider whose docs describe an OpenAI-compatible surface is
  configured as such rather than hand-written per provider.

Interface: one `Protocol` per provider-shaped concern (metadata check, model listing) so tests
can substitute a fake without HTTP, per the Context Pack's "isolate behind an interface".

Tests for A: a table-driven test that **every** registry entry has every field and a unique
`name`/`env_var`; a test that a brand-new fake registry entry (added in the test, not in the
product) is accepted by `KeyStore.entries()`, `target_for`, discovery and the executor path with
no code change — that test is the proof that "adding a provider is data plus a test".

#### Free/paid classification (the rule that keeps "free = $0" honest)

Every provider declares `tier` in its registry entry, and **no paid provider may masquerade as
free**:

- `free_cloud` means the documented call costs the user **$0** — OpenRouter `:free`, anonymous
  Pollinations, a documented free plan. "Included credits", "trial credit" and "cheaper" are not
  free.
- `paid` means a bill or a credit balance is consumed.
- Unknown → `paid`, with an ASSUMPTIONS row. Never the other way round.
- The discovered models inherit the provider's tier; a model that the provider's own listing
  marks as free (e.g. a `:free` suffix) may be `free_cloud` inside a `paid` provider — but only
  when the listing says so, and it goes in the catalog as data, not as a slug check in code.

**`scope.py`'s `paid_scopes` gate does not affect free providers, and say so plainly in the
report:** `headwaters/core/scope.py` gates the ★ `paid_scopes` feature (`paid_scopes_available`),
and a key alone never puts a paid tier into scope. Free tiers (`free_cloud`, `local`) are
unaffected by that gate, so a user with no keys at all can still route every request this ticket
adds. Nothing here loosens a lock, and Private lock and project rules still win (v3.3 §A, §C).

#### Accept when

- Every shipped provider can be selected by routing for a **free-scope** request
  (`headwaters/free` and `headwaters/auto` in free scope), is listed in the dashboard with an
  honest source, and is testable (`headwaters keys test <provider>`).
- Every provider that could **not** be verified is **absent** from the code and documented

- Adding a provider is data plus a test: a fake registry entry added in a test flows through the
  key store, `keys test`, discovery and the executor with no product code change.
- No paid provider is scored `free_cloud`; Pollinations needs no key; Mistral's paid keys never
  reach the free scope; OpenRouter `:free` and OpenCode free behave exactly as before.
- No new hard-coded model slug, limit, price or error regex: those stay in the catalog or
  rules.yaml.

#### Out of scope

New dashboards or tray UI (HDW-503 and HDW-504 already render whatever the key store knows),
paid-tier routing changes, `paid_scopes` behaviour, and any provider whose docs do not exist yet.

#### Provider identity (binding, D18; every line here is an accept-when)

The registry from Slice A is the **named owner of provider identity** for the whole product
(decision D18 in `docs/DECISIONS.md`). HDW-503 (dashboard) and HDW-504 (tray) **consume** it
through `KeyStore.providers()`; neither keeps a provider list or a label of its own, and the CLI
reads the same set.

- **Canonical ids.** Each entry's `name` is the one plain, lowercase id used everywhere a
  person or a program names a provider. Shipped set: `anthropic`, `openai`, `openrouter`,
  `nvidia`, `huggingface`, `mistral`, `pollinations`, `opencode`, `kilo`, plus keyless
  `ollama`. A new entry's `name` is a product name, never an environment variable spelling.
- **The `env_var` mapping is internal-only.** It is read to find a key in the environment and
  to register the entry; it is never part of any text a person reads: not in the CLI, not in
  the dashboard (HDW-503), not in the tray (HDW-504), not in `headwaters keys` output, errors,
  `doctor`, logs a person is told to read, or docs. This **overrides** the "Provider docs page"
  bullet above: that page lists supported providers by canonical name and says what free means
  for each, and does **not** list an environment variable.
- **`headwaters keys set <name>` must not silently accept an unknown provider name.** A name
  that is not in the registry (after normalisation below) fails with a non-zero exit and a
  message that lists the canonical names, creates no key record and writes nothing to the
  credential store. The existing `openai_compatible[*].name` providers stay valid names.
- **Environment variable spellings a person types are normalised to the canonical id.** If a
  person types `HF_TOKEN` or `NVIDIA_API_KEY` (any case) as a provider name, the CLI resolves
  it through the registry to `huggingface` or `nvidia` and carries on, and everything it says
  back uses the canonical id. The lookup uses each entry's own `env_var` (so it needs no
  second table) and is accepted on input only; it is never listed as an alternative name.
- **Human-facing strings never print a variable name.** That includes the "key not set" and
  `keys test` messages, the `unknown provider` message above and `doctor`. When a message
  must point at where a key comes from, it says "your system environment" and the canonical
  id.
- **Tests.** A table-driven test over every registry entry asserts the entry's `env_var` is
  absent from the text of every message the CLI can print for it (set, test, remove, list,
  unknown) and that an env-var spelling resolves to the canonical id; one test asserts an
  unknown name exits non-zero and creates no record; the Slice A fake-entry test also asserts
  the fake entry's `env_var` never appears in rendered output.
- **Consumers.** HDW-503 and HDW-504 add the matching tests on their surfaces ("Provider
  identity" in each packet); neither ticket starts a provider list of its own.

### Excerpt: v3 design §4.2

#### 4.2 Catalog
Three layers, merged in this order:
1. **Live discovery**
   - Ollama: `/api/tags`, `/api/show` (capabilities, `model_info` architecture params for KV math, context), `/api/ps` (which model is warm)
   - OpenRouter: `/api/v1/models` (modalities, supported parameters, context, pricing, `:free`), `/api/v1/images/models` (image generation), `/api/v1/key` (credit and limits)
   - OpenCode: free models from the OpenCode config/provider listing, or a user list
   - Other free providers the user adds (OpenAI-compatible)
2. **Curated catalog** (`catalog.json`, signed, versioned). Contains per-task quality scores, `agentic_tools` reliability, known free-tier limits, deprecations and renames, Ollama tag aliases, and recommended local models per GPU profile. It is fetched from your GitHub releases at startup (with an ETag) and **works offline with the last cached copy**. This is the main way to cut support load: when models change, you ship data, not a new build.
3. **User overrides** in `rules.yaml`.

Unknown models get conservative default scores, labelled "unscored" in the dashboard.

### Excerpt: v3.3 addendum §A

## A. Routing model: scope × strategy × locks
The earlier `mode` mixed two different things. They are now separate:

| Axis | Question it answers | Values |
| --- | --- | --- |
| **Scope** | *Which tiers may serve this request?* | `auto`, `free`, `local`, `cloud` |
| **Strategy** | *How do we rank inside the scope?* | `cost_saver` (default), `quality_first`, `primary_first` (was `paid_only_until_wall`) |
| **Locks** | *What can never be loosened?* | Private lock, project privacy rule, secret detection |

`local_only` is no longer a mode. It is the `local` scope, optionally enforced by the Private lock.

### F1. Positioning: where Headwaters wins
1. **"Headwaters Auto" inside Copilot's picker, working in agent mode**: smart, scoped routing where Copilot users already are.
2. **GPU-aware local intelligence**: VRAM and KV-cache fit, computed `num_ctx`, warm-model preference, sysmem-fallback detection, battery awareness.
3. **Verify-then-escalate with safe defaults**: answers as diffs, no direct writes by local models unless the user opts in.
4. **Guaranteed scopes**: `free` = $0, `local` = provably private (fail-closed, egress-tested), plus the Private lock.
5. **Windows-first product polish**: one-click installer, wizard, tray, doctor, signed builds.
6. **One engine for every IDE**: gateway + MCP + extension share state, walls and savings.

> Point 4 is why this ticket's classification rule is strict: "free = $0" is a promise on the
> store page, so a paid provider scored as free would be a false claim, not a routing bug.
