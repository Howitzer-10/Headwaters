## Summary
Windows packaging is now a program around the CLI that already exists, not a second front end.
`packaging/innosetup/headwaters.iss` installs per user into `{localappdata}\Headwaters`
(`PrivilegesRequired=lowest`, no HKLM, no admin) and ships only `uv.exe`, `uv.lock`,
`pyproject.toml`, `headwaters\` and `catalog\`; the private venv is created on the target machine by
`uv sync --frozen --no-dev --python 3.11`, so no Python, no weights and no PyInstaller one-file build
is bundled. `headwaters/packaging/` owns the rest behind plan/apply seams: `layout.Install` for the
paths and the update mode, `runtime` for the sync/run commands, `autostart` for the at-logon task as
XML plus the exact `schtasks` argv, `uninstall` for an owner-split removal plan, `itch` for the
`[[actions]]` manifest, and `build` for staging, ISCC and the signing hook. The uninstaller deletes
the task, then `{app}\runtime`, and asks before removing state or keys (`--remove-state
--remove-keys` through `headwaters.packaging.uninstall`). Signing is a hook: it signs only when
`HEADWATERS_CERT_PATH` is set, redacts the password, and otherwise says so and finishes unsigned.

## Assumptions
- The row this ticket added to docs/ASSUMPTIONS.md is the authority: the install root is the
  per-user state dir and the venv is created on the target machine from the bundled uv and lockfile,
  the uninstaller removes the task and `{app}\runtime` by default and state/keys only after consent,
  removal is split by owner because a process cannot delete the runtime holding its own
  `python.exe`, the at-logon task is generated XML registered with `schtasks`, the itch payload runs
  `runtime\uv.exe run --frozen --no-dev --project runtime headwaters ...`, signing is a hook gated on
  `HEADWATERS_CERT_PATH`, and every side effect sits behind an injectable plan/apply seam.
- The itch manifest and Inno Setup facts are recorded in docs/SDK_FACTS.md (new section "itch.io
  packaging (HDW-405)") instead of being repeated here: `.itch.toml` paths resolve relative to the
  manifest's own folder, `butler push <dir> <user>/<game>:<channel>` names the channel, and
  `PrivilegesRequired=lowest` plus `CurUninstallStepChanged(usUninstall)` are the Inno features the
  installer depends on.
- **One assumption is deliberate and unverified:** the working directory an itch action is launched
  in is not documented anywhere I could read, so the actions pass relative paths only and also give
  the CLI an explicit `--project runtime`. If the itch app launches them from the payload's parent,
  the manifest needs `runtime/` prefixes; that is FU-405-3 and `butler validate` is the check.
- No SDK source was read for this ticket: the facts came from the official itch app, butler and Inno
  Setup documentation, so the SDK-source read budget was unused (0 of 5).

## Deviations
- **`headwaters status --open` is new.** The packet asks the itch actions to open the status page, and
  HDW-404 shipped the page but no way to reach it from the CLI. `--open` reuses a running daemon or
  starts one (`status_page_url`) and then opens the dashboard URL in the browser; the table is
  skipped, `--json` prints `{"ok": true, "url": ...}` and still opens nothing. Everything else about
  `status` is unchanged, and the Start-menu shortcut uses the same flag instead of new code.
- **The doctor gained an `install` check**, and two doctor tests pin the check ids positionally.
  `tests/test_doctor.py` asserts the exact list of ids, so it was extended by inserting the single
  literal `"install"`. `tests/test_doctor_cli.py::test_doctor_json_is_the_report` asserted
  `ids[:3] == ["environment", "ollama", "ollama_env"]`, which the new check moved to index 1; it now
  asserts `ids[:4] == ["environment", "install", "ollama", "ollama_env"]`, one exact replacement, and
  no other assertion in that file changed. Nothing else in the full suite depended on the order.
- **Four `.importlinter` contracts and `tests/test_import_contract.py` were extended** for
  `headwaters.packaging`: it is forbidden from `headwaters.core`, and it is a source of the MCP, web
  framework and daemon contracts. Its own test lists (`SUBPACKAGES`, `CORE_FORBIDDEN`) were updated
  by exact replacement to match.
- **Removal is split by owner rather than listed once.** `uninstall.plan()` marks the task and the
  runtime `OWNER_INSTALLER` because `python.exe` cannot delete the tree it is running from, and only
  the state dirs and keys `OWNER_PYTHON`; `apply_optional()` additionally refuses any path outside
  `Install.roots()`. The single `uninstall` command therefore cannot silently remove an install.
- **The itch install actions pass `--yes`.** `headwaters install` asks for consent by design
  (HDW-403); a launch action that stops to ask inside the itch app cannot prompt for a terminal, so
  the action carries the flag that the CLI already accepts.
- **`packaging/.gitkeep` is gone**, because `packaging/` now holds the Inno script, the manifest and
  the butler script.
- **`docs/RELEASE_CHECKLIST.md` is new at that path** because the accept-when names it; it is the
  owner's document, and its section 2 is the clean-VM run this session could not perform.

## Follow-ups
- FU-405-1 | signing | `headwaters/packaging/build.py` `signing_plan` | The certificate itself is the
  owner's: an Authenticode signing certificate and its password must be supplied through
  `HEADWATERS_CERT_PATH` (plus `HEADWATERS_CERT_PASSWORD` and, for another signer,
  `HEADWATERS_SIGNTOOL`). Until then the build prints that it is skipping signing and ships an
  unsigned setup exe, which Windows SmartScreen will warn about on first run.
- FU-405-2 | itch | `packaging/butler/push_windows_beta.ps1` | The upload has not been run: butler is
  not installed in this session and the script is deliberately not wired into pytest or CI. Follow
  section 3 of docs/RELEASE_CHECKLIST.md (`-Validate`, then the push to `windows-beta`) once the
  channel exists on the game page.
- FU-405-3 | itch | `packaging/itch/.itch.toml` | The itch app's launch working directory is
  undocumented, so the manifest assumes the payload root and passes relative paths. `butler validate`
  plus one real install must confirm it; if the app launches from the payload's parent, the action
  args need `runtime/` prefixes.
- FU-405-4 | installer | `packaging/innosetup/headwaters.iss` `[UninstallRun]`/`[UninstallDelete]` |
  A running daemon holds `runtime\.venv\Scripts\python.exe`, so `[UninstallDelete]` can fail to
  remove `{app}\runtime`. The uninstaller should stop the daemon (an existing CLI command) before the
  task is deleted, and a failed delete should be a reboot-scheduled delete rather than a silent
  leftover.
- FU-405-5 | autostart | `headwaters/packaging/autostart.py` `DEFAULT_ARGUMENTS` | `headwaters start`
  at logon flashes a console window for as long as it runs. A windowless entry (`pythonw.exe`, or a
  start that daemonises and exits) belongs with the tray app rather than in this ticket.
- FU-405-6 | tray | `headwaters/cli/` | A tray icon that opens the page, shows the scope and toggles
  the at-logon task was out of scope; the Start-menu shortcut plus `status --open` cover the same
  ground from the CLI for now.
- FU-405-7 | installer | `headwaters.iss` `[Icons]` | The shortcuts point at
  `runtime\.venv\Scripts\headwaters.exe`, a shim that embeds an absolute interpreter path. That is
  fine for an in-place upgrade and the reason the itch payload uses `uv run` instead; regenerating
  the shortcuts through uv would make both paths identical.
