## Summary

The gateway now serves the Anthropic Messages API at `POST /v1/messages` beside the OpenAI face, on
the same port, the same daemon token and the same `RouteRequest` path, so Claude Code can point
`ANTHROPIC_BASE_URL` at `http://127.0.0.1:4000`. Text, tool use and streaming are checked with the
real `anthropic` SDK against the HDW-148 rig's scripted provider and against a router stand-in, and
the routing headers, the error advice and the failover plumbing moved into `headwaters/gateway/shared.py`
so both faces share one copy.

## Deviations

- **D7 and the translation layer.** D7 chose the litellm SDK behind a thin gateway (not the LiteLLM
  proxy) and names `litellm.anthropic.messages.acreate` for this endpoint. `.importlinter` confines
  litellm to `headwaters.core.executor.cloud`, and that backend speaks OpenAI-shaped messages, so the
  translation is hand-written around the router instead — the packet's own second branch. The router,
  which owns failover before the first token, the verification gate, the routing headers and the
  session pin, has to sit in the middle; calling litellm's Anthropic helper directly would bypass all
  of it.
- **`x-api-key` on the guard.** The packet does not say the daemon token may arrive in `x-api-key`,
  but the Anthropic SDK sends nothing else, so `GuardedApp` had to accept it. It is the same token,
  compared in constant time; `Authorization: Bearer` still works on both faces.
- **529 instead of 503 for a router that is not ready.** Anthropic's own overload status is 529
  (`overloaded_error`), so the Messages face answers 529 where the OpenAI face answers 503. Both
  surface as `APIStatusError` in the respective SDK.
- **`anthropic` is a dev dependency, not a runtime one.** Only the tests import it; the gateway
  translates by hand.
- **`claude-haiku-4-5` as the pinned model name in the translation test.** `claude-sonnet-4-5` makes
  the SDK emit a `DeprecationWarning` on every call (`anthropic/_data/deprecated_models.py`).
