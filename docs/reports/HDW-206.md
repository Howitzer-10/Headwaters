## Summary
The three model tools (`headwaters_do`, `_ask`, `_think`) now plan each call before running it (a
dry run through `Router.plan`: no model call, no write). A call expected to take longer than
`mcp.async_threshold_s` (or passed `async: true`) runs as a background job and returns a `job_id`;
its state is in the SQLite `jobs` table and `headwaters_job_status` / `_job_result` read it. Every
other call runs now and sends MCP progress notifications (a step counter, a heartbeat while a step
is slow, a "cold start" message for a model that has to be loaded). A call whose expected spend is
over `budget.confirm_above_usd`, or that asks for a wider scope than the default, asks the user
through elicitation; a host that cannot be asked gets `confirmation_required` and the exact
`force: true` follow-up, and nothing runs or is spent until then. The stdio shim now forwards the
daemon's progress to its host.

## Deviations
- The spec Tasks primitive is not used. A-MCP-4 says it is an extension a client must declare and host support is unverified, and D9 keeps the `job_id` pattern as the baseline; the ticket allows this ("else the `job_id` pattern").
- Progress carries a step counter with no total, not a percentage, because MCP needs `progress` to rise on every notification and a retry or cascade would otherwise send it backwards. The 0..1 fraction is in the job row.
- Scope loosening by `headwaters_scope` already had elicitation and a text fallback (HDW-205). HDW-206 applies the same rule to a per-call `scope` argument of `do`, `ask` and `think`, plus spend; `headwaters_scope` itself is unchanged.
- `headwaters_think` moved from `frontdoor_more.py` to `frontdoor_run.py` so the three model tools share one guard. No behaviour change beyond the new guard.
- `flow.run_model_tool` is kept; `prepare_request` and `run_prepared` were split out of it so the estimate and the run use one prepared request.
- No conflict with D7 to D14. D8 and D14 hold: the SDK is imported only inside `headwaters/mcp/`; the daemon imports no SDK.
