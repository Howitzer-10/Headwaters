## Assumptions
`docs/ASSUMPTIONS.md` carries one row for this ticket (2026-11-05) covering the doctor's checks,
the bundle's allowlist, the daemon exit-code triage and the six carried follow-ups. One new SDK
fact was verified and lives in `docs/SDK_FACTS.md` instead of being repeated here: mcp 2.3's
`Client.call_tool(..., meta=RequestParamsMeta)` keyword, which the host probe uses to stamp the
request.

## Deviations
- **The broken credential store is not detected.** `KeyStore._get`/`_delete` swallow every backend
  exception, so a locked or unreachable store reads as `source == "not set"` and the doctor reports
  the keys check as SKIP rather than FAIL. The test for a broken store therefore uses a stub whose
  `entries()` raises, not `BrokenKeyring` (FU-402-1).
- **Existing tests grew, they were not rewritten.** `tests/test_daemon_control.py` and
  `tests/test_cli_daemon.py` gained ten and two cases; no existing assertion or count changed, so
  no replacement was needed.
- **`headwaters stop --force` is a behaviour change, not a new command.** Plain `stop` still never
  kills a pid it did not start; `--force` does, and refuses when the pid is the current process.

## Follow-ups
- FU-402-1 | keys | `headwaters/core/keys.py` `_get`/`_delete` | Let a backend failure surface as a
  distinct `source` (for example `"unavailable"`) so the doctor can FAIL instead of SKIP on a
  locked Windows Credential Manager; today every backend error is swallowed.
- FU-402-2 | doctor | `headwaters/control/doctor.py` `_mcp_launch` | The doctor proves the
  `headwaters-mcp` command resolves and that the tool list answers, but it does not validate a
  host's own config file; the installer checks (FU-202-5) belong with HDW-403's host adapters.
- FU-402-3 | report | `docs/reports/HDW-402.md` | The report format has no field for the `--bundle`
  zip's own size or member count; a later doctor change can grow the bundle silently.
