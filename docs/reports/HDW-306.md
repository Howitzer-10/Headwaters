- `test_the_private_lock_stops_the_gateway_before_any_client` accepts `private_lock_conflict` or `pin_rejected` as the 400 code: on the OpenAI face the explicit cloud model is a pin, and the pin check (which sees the narrowed pool) runs first. ## Independent review (local-scope sign-off)

Reviewed on branch `howitzer-10-hdw-306-privacy-egress-tests` at `f0464c3`, read-only, by the
coordinator (the packet's Opus review step). **Signed off: no code path constructs a cloud client
in local scope.** Evidence:

- Cloud backends are constructed in exactly two places package-wide: the default
  `cloud_factory: Callable[[], Backend] = LiteLLMBackend` in `headwaters/core/engine.py#build_engine`
  (a class reference, not an instance) and `Executor._prepare`, `self._cloud = self._cloud_factory()`
  at `headwaters/core/executor/executor.py:155`.
- That line is unreachable for a local target: `_prepare` runs `enforce_scope(decision, rules,
  remote_patterns)` first, then returns `self._local_factory(...)` in the `decision.tier == "local"`
  branch before the cloud branch. `_events` obtains its backend only through `_prepare`, and
  `_collect` only through `_events`, so there is a single backend path.
- `enforce_scope` (`headwaters/core/executor/guard.py`) refuses `local_only` scope with a non-local
  tier, any tier outside `decision.scope.tiers`, `private_lock`, `airplane`, and a local tier whose
  model is an Ollama cloud-proxied name or whose host is not a plain-http loopback URL.
- Direct network clients outside litellm: only the Ollama client (`headwaters/core/executor/ollama.py`,
  loopback host asserted by the guard) and `urllib` in `headwaters/core/catalog/updater.py`, gated by
  `blocked_reason` on airplane and local-only lock state. Nothing in `headwaters/features/` or the
  daemon builds a provider client.
- Test-side proof is construction-level, not call-level (`cloud_clients`/`cloud_calls` count factory
  invocations), and the audit hook is independent of the mock wiring.

Low-severity observation, not a sign-off blocker: `enforce_scope` re-reads `private_lock` and
`airplane` live (HDW-131) but `decision.scope` was resolved from the rules at decision time, so a
user switching `default_scope` to `local` while a cloud-tiered request is already decided does not
stop that one request. This matches the documented engine-rebuild behaviour (an in-flight request
finishes on the engine it started on) and nothing is constructed for a request that *begins* in
local scope; noted for FU-306-1 rather than treated as a defect.
