## Summary

A three-word Cline prompt against `headwaters/local` failed with "Only local models are allowed
here, but none is available. pull qwen2.5-coder:14b" because the request's `tools` array — two MCP
servers' whole catalogues plus Cline's own schemas — was counted as 57,794 tokens of code, which
with the 1.2x headroom asks for 69,353 against a 65,536 local window. The message blamed
availability and named a model that was already installed.

Slice A makes that failure legible. A context shortfall is now detected from the rejection reasons
(never from a guess), the request's cost is split into tools / message+system / images with the same
estimator the analyzer used, the largest tool namespaces are named, and the message lists the fixes
that work. A `pull <model>` suggestion is removed whenever the shortfall is context; when a model
really is missing the old hint is untouched.

Slice B adds `tools.prune_to_fit` (default **false**). Switched on, a local-only request whose only
obstacle is schema volume drops the largest non-`headwaters` namespaces — cumulatively, so the
smallest number of drops does it — and re-runs analysis and the normal decision path on the pruned
request. What it dropped is appended to the decision reasons, so `headwaters explain` and the
dashboard show it. The `headwaters_*` front-door tools are never dropped, the free and cloud tiers
never prune, a request whose message or images alone exceed the window is never pruned, ambiguous
attribution refuses to prune, and when nothing fits even after dropping everything droppable the
original error stands and the caller's request is untouched.

What did not change: the analyzer's arithmetic (the schemas are still counted, honestly), the
policy ladder, `hard_filter`, scope resolution, locks, walls and quotas. Pruning is a second run of
the existing path on a smaller request, not a second routing rule.

## What the error says now

The dogfood case, rebuilt as a unit test (`tests/test_router_tool_cost.py`) with 117 schemas whose
serialised size reproduces a 57,794-token request, a 65,536-token local window and
`ctx_headroom` 1.2:

```
The request needs 57,794 tokens of context; with the 1.2x context headroom a model must hold
69,353, and no local model can. The largest local window is 65,536. Composition: tools 57,784
tokens (117 schemas), message/system 10, images 0. Largest tool namespaces: summer 57,210 (109
tools), headwaters 574 (8 tools). Fix: use a wider scope such as headwaters/auto, set
tools.prune_to_fit: true in rules.yaml or remove a large MCP server from the host.
```

There is no `pull <model>` anywhere in it. With pruning on and enough headroom, the note reads
`tools pruned to fit a local model: dropped summer (44,271 tokens)`.

## Deviations

- `headwaters_ticket_packets/HDW-408.md` does not exist in this repo, so the house style was read
  from `headwaters_ticket_packets/HDW-208.md` plus `docs/reports/HDW-208.md` and
  `docs/reports/HDW-408.md`. No effect on the work.
- The attribution rule is narrower than "the longest shared prefix of the remaining names", which
  would give one namespace for a two-server array (`summer_add_node` and `headwaters_do` share no
  prefix) and make pruning impossible in exactly the dogfood case. It is: `__` split when present;
  otherwise the leading `_` segment, which is how a flattened MCP name carries its server; for a
  single server the shared prefix is still used, so `mcp_alpha_*` reads as `mcp_alpha` rather than
  `mcp`. Ambiguity still fails closed, which is the property the ticket requires.
- `tests/router_support.py`, `tests/router_rig.py` and `headwaters/cli/runtime.py` are not in the
  packet's file list: the composition needs `estimate_tokens` on the analyzer the rig and the CLI
  use, and the rig needs to hand the router a candidate pool.
- No `docs/DECISIONS.md` conflict found; no decision changed.
