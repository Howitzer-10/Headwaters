## What the ticket asked for

Register two distinct products with two distinct endpoints — `opencode` (Console, account
authenticated) and `opencode-go` (the Go plan, static key) — with tiers grounded in evidence rather
than optimism, plus the correction of assumption **A-OC-3**, which HDW-514 used to defer OpenCode.

Both names are now catalog data. Neither is `free_cloud`, and the report says why below.

## Per slice

**Slice A — packet.** `headwaters_ticket_packets/HDW-515.md` in HDW-514's shape: Part 1 holds the
brief, the Cline observations as *observations*, the A-OC-3 correction, the facts verified for this
ticket and the limits; Part 2 is the normative slices with accept-when lines; Part 3 is the
per-provider verification protocol that has to run before any code depends on a new fact.

**Slice B — registry rows.** `opencode` and `opencode-go` are two rows in `providers`, each with its
own `base_url`, `models_endpoint`, `metadata_url`, `source_url` and `checked: 2026-11-03`. Both
declare `OPENCODE_API_KEY`, which the catalog previously rejected as a duplicate: `_cross_references`
no longer rejects a repeated `env_var`. `KeyStore` was already keyed by provider name, so a key
saved for `opencode` never answers for `opencode-go`, while a variable in the environment reaches
both — that is the observed reality and it is what the tests pin. `opencode` was also in
`RESERVED_PROVIDER_NAMES` (a name that could not be registered); it is removed from that set, with
the data-driven refusal taking its place.

**Slice C — tier truth.** Both rows are `paid`.
* `opencode` (Console): the listing is public and lists nine ids ending `-free` at cost 0, but the
  Console docs say free-tier chat models "are only available from within OpenCode; other clients
  receive HTTP 403, even with an API key". Customer list price is pay as you go. The `-free` ids are
  therefore dropped at discovery (`skip_id_pattern: "(?i)-free$"`) and refused if asked for by name.
* `opencode-go`: a subscription (Go, Go Plus, Go Teams). Beam Free and Iceman Contributor Free are
  included at $0 per call, but the plan is not free — the same reading HDW-514 applied to Hugging
  Face included credits.
The decisive keyed probe was **not run**: `OPENCODE_API_KEY` is not set in this environment.

## A-OC-3, corrected

The old row said free models exist but "no machine-readable list endpoint found". That clause was
wrong: both products publish a listing (`/inference/v1/models`, `/inference/go/v1/models`) that
answers 200 anonymously and marks the free ids at cost 0. The 403 HDW-514 saw was not anonymity
either: it is the OpenCode client that gates those ids, and the docs say an API key does not change
it. So HDW-514's decision — do not offer the free ids — stands, for a partly different and now
stated reason, and the reachability of those ids from Headwaters with a real key remains unverified
rather than assumed either way.

## Correction, 2026-11-03 (HDW-515 continued)

The ticket was reopened to amend its own conclusions. Everything above is left as written; this
section says what is no longer true and what replaced it. The probing is recorded as SDK_FACTS rows
under "Live probe, 2026-11-03 (amends HDW-515)".

### What was wrong

1. **The 403 was never an auth gate.** `GET` on both listing endpoints returns 200 anonymously *and*
   with a key (80 models on Zen/Console, 28 on Go). What HDW-514 and this ticket saw was Cloudflare
   rejecting a generic HTTP-library user agent: plain `urllib` (`User-Agent: Python-urllib/3.x`) gets
   403 with `error code: 1010` on every OpenCode host, with or without a valid key, and the same
   request with a product user agent returns 200. The OpenCode Go docs ask clients to identify
   themselves "with its own user agent, such as my-coding-agent/1.0, rather than a generic SDK or
   HTTP-library name". So the 403 was a *client* gate, not an account gate.
2. **The reason the free ids are refused is a 429, not a 403.** `POST {zen base}/chat/completions`
   with `deepseek-v4.1-flash-free` (and `beam-free`) returns 429 `FreeUsageLimitError`: "Free usage
   limit reached. Free models work in OpenCode (https://opencode.ai); subscribe to OpenCode Go to
   keep going". Identical with a valid key, without a key, with a correct user agent and with the
   session header. The conclusion in "Decision" above — do not offer them — stands; only its stated
   reason was wrong. They are app-only, and that is now argued from the 429.
3. **OpenCode Go could not be called at all, and nothing noticed.** `POST {go base}/chat/completions`
   without `x-opencode-session` returns 400 `MissingSessionID`: "Request is missing
   x-opencode-session and cannot be routed efficiently". With a stable per-conversation session id
   the same request returns 200. A plain bearer-style OpenAI-compatible call — which is what the
   executor sent — therefore failed on every request, so the Go row would have broken in production
   on its first real call. This is the defect the amendment exists to fix.
4. A Go 200 carries a real per-call cost signal that no other non-OpenRouter provider gives:
   `usage.opencode = {billing_source: "go", list_cost, allowance, tokens{...}}`. A sample call
   reported `cost 0`, `list_cost` ~1e-05, `allowance` ~8e-06 — drawn from the Go subscription
   allowance at zero marginal cost.

### What changed in the code

- `headwaters/core/user_agent.py` (new): one product user agent, `headwaters/<version>`. The catalog
  discovery fetch uses it, and so does every outbound provider call.
- `ProviderEntry.session_header` (schema, with a pattern) and `ExecTarget.session_header`: a catalog
  row may declare a per-conversation header. `TargetBuilder` passes it through, `Executor._prepare`
  fills it from the router's session key, and a call with no conversation id is refused with
  `ExecutorError("session_required")` rather than sent. Nothing in the router or the executor names
  a provider: the Go row is data.
- `headwaters/core/router.py` passes `conversation_id=run.key` at both call sites, so the header is
  stable for the life of a conversation and distinct across conversations.
- `catalog/seed_catalog.json`: `opencode-go` declares `session_header: "x-opencode-session"`; both
  rows keep `tier: paid` (a Go subscription is money — a paid *tier*, and per the newer decision
  text a paid *product* would additionally need an entitlement system this project does not have),
  and both `free_notes` now state the 429/app-only reason and the 403 history accurately instead of
  repeating the auth-gate claim. The schema was regenerated.
- `docs/ASSUMPTIONS.md`: A-OC-3 corrected in place with a dated correction row;
  `docs/PROVIDERS.md`: both provider rows and the "add a provider as data" field list;
  `headwaters_ticket_packets/HDW-515.md`: an amendment note and the new field.

### What changed in the tests

`tests/test_hdw515_opencode.py` gained a session-header/user-agent section: only the Go row declares
a header, the target carries the header the row names, a Go call puts the conversation key on the
wire, a Go call without a conversation id is refused, a Console call sends no session header, every
provider call names Headwaters (checked against a list of generic library names), discovery uses the
same agent, and the router keys the header to the conversation. `tests/test_discovery_sources.py`

agent in the prepared headers; `tests/router_rig.py` gained a resolver override so the router test
can route to a Go target.
