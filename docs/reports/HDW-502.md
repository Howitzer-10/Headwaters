## Summary

`headwaters/features/paid_scopes/` is now a ★ module that (a) lets paid tiers into `auto` and
`cloud` when it is enabled, (b) holds a daily spend cap against `rules.budget.paid_daily_usd`, and
(c) turns a below-floor, paid-less answer into one advisory line plus a handoff packet. Core grows
three seams and still never names the feature: two plugin interfaces (`BudgetPlugin`,
`AdvicePlugin`), `headwaters/core/paid_scopes.py` to look them up, and `RouteDecision.advisory` to
carry the line to both surfaces. Everything the feature needs — spend, rates, the cap, the packet —
it reads through the registry's services, so deleting the folder or `features: {paid_scopes: false}`
returns `auto`/`cloud` to exactly the behaviour they had on master (tested in both states, and with
the package removed from discovery).

The four pre-coding probes changed the design in three places, and the packet was materially wrong
about two of them:

- **P1 — the paid tier was already excluded everywhere, by a gate with nothing behind it.**
  `core/scope.py:35` declares `PAID_SCOPES_FEATURE_ID = "paid_scopes"` and `:116`
  `paid_scopes_available(registry)` → `registry.enabled("paid_scopes")`, and `resolve_scope()`
  (`scope.py:279-281`) is the single choke point that strips `PAID_TIERS` and records
  `"paid tiers excluded: the paid-scopes feature is not enabled"`. `paid_scopes_available` is called
  from `core/router.py:365,435` (`_local_only_scope` and the walls), `control/status_page.py:43,256`,
  `cli/cmd_status.py:21,111` and `mcp/tools/status.py:18,48` — every path that computes a scope. So
  the gate was already uniform and correct; what was missing was a package that registers the id,
  which meant `enabled()` was **always False** and no run could ever see a paid model. Tests had
  been faking the registration by hand (`tests/router_support.py registry_with(paid=True)`). This
  ticket adds the real package and leaves the gate alone: no core file gained a "is the feature
  installed" branch.
- **P2 — `paid_daily_usd` was inert, `confirm_above_usd` was not.** `core/rules.py:83-87`
  `BudgetRules(premium_max_usd_per_call=1.00, paid_daily_usd=5.00, confirm_above_usd=0.25)`.
  `confirm_above_usd` is live and already flows the MCP guarded path (`mcp/tools/guarded.py:95,107,121`,
  `render_run.py:23-24`, `schemas.py:74-75`, `estimate.py:6`) — the packet's second budget item
  needed no work. `paid_daily_usd` had **no reader at all**. The data to enforce it exists: per-day
  `outcomes.cost_usd` joined `outcomes.decision_id = decisions.id` with `decisions.ts`. Because
  core may not import `headwaters.features.*` (import-linter), the cap lives in the feature, and it
  reaches catalog rates through `core/catalog/schema.py` `ModelEntry.price_in/price_out/price_date`
  and the existing `core/router_log.cost_usd` / `policy/scoring.estimate_cost_usd` conventions. The
  catalog is the owner of the rates; the feature reads it, nothing in core does.
- **P3 — advice and handoff mostly existed; the quality floor is scoring's.** `rules.advice:
  "off"|"inline"|"header_only"` (`rules.py:503`) was read in exactly one place,
  `gateway/shared.py`, where `meta_headers` always sets `ADVICE_HEADER` from `advice_note()` and
  `headwaters_meta` carries the note only when `inline` — the three-way already worked, but only
  `BELOW_FLOOR_WARNING` ever travelled it. `core/advice.py` exports `BELOW_FLOOR_WARNING`,
  `UNCHECKED_NOTE`, `STREAMED_VERIFY_NOTE`, `REMOTE_IMAGE_ADVICE`. `hosts.subscription:
  dict[str,bool]` existed (`rules.py:467-470`) with no reader. `sessions.handoff_packet_id` exists
  (`state_schema.py:42`) and a writer does exist in core: `state_misc.add_handoff`, `get_handoff`,
  `latest_handoff_id`, with `pin_session`/`upsert_session` able to stamp the column — so the packet
  only had to add `link_handoff`, not a handoff subsystem. **The quality floor is
  `core/policy/scoring.floor_for` / `meets_floor` / `ScoreBreakdown.meets_floor`/`below_floor_by`
  over `rules.floors`**, and the router already records `decision.below_floor` — the advice triggers
  off that flag, not off a second floor computation.
- **P4 — what a ★ package must export.** Module-level `register(registry)`;
  `discover_features(registry, package="headwaters.features", include_private=False)` walks
  `pkgutil.iter_modules` over the package, imports each subpackage by name and calls its `register`,
  skipping `_`-prefixed names. `register` calls
  `registry.register(FeatureSpec(id, star=..., title=..., interfaces=(...), default_enabled=True),
  {"InterfaceName": instance})`; `FeatureSpec.__post_init__` validates every interface name against
  `INTERFACES`, and a duplicate id raises `ValueError`. `enabled(id)` is
  registered ∧ `_flags.get(id, spec.default_enabled)`, and `plugins_for(interface)` returns enabled
  instances ordered by feature id. `headwaters.features.ledger` (landed today) is the worked example
  for services: the package itself takes nothing from the registry beyond `services={db, catalog,
  rules}`, which `core/engine.py:241` supplies. Discovery now reports
  `['headwaters.features.ledger', 'headwaters.features.paid_scopes', 'headwaters.features.tray']`,
  and `paid_scopes` is declared as `FeatureSpec('paid_scopes', star=True, default_enabled=True,
  interfaces=('BudgetPlugin','AdvicePlugin'))` — switchable off by flag and removable by deletion.

## Assumptions

- A-xxx added to `docs/ASSUMPTIONS.md`: none — every figure the cap uses is read from the state
  database, the active catalog and `rules.budget`, so nothing new is assumed.
- No new SDK fact was verified for this ticket (the four probes were all repo-internal, and no SDK
  source was read), so no row was added to `docs/SDK_FACTS.md`.
- **The cap is checked before the call, against an estimate, not after it.** `check()` compares
  `spend + max(estimated_usd, 0)` with the cap, so a call can still take the day past the cap by up
  to its own cost; the alternative (refuse after spending) buys nothing. The estimate reuses the
  router's existing convention (`policy/scoring.estimate_cost_usd`, `rules.scoring.assumed_output_tokens`).
  FU-502-4.
- **Day boundary is UTC midnight** (`day_start(now)`), matching `decisions.ts` being UTC and the
  ledger's day grouping. `budget.paid_daily_usd` therefore resets at 00:00 UTC, and the refusal line
  says so.
- **An unpriced paid-tier request is counted, not costed.** A paid-tier request whose model the catalog does
  not rate cannot be priced from `outcomes.cost_usd` alone (it stores `0.0`) — the same ambiguity
  HDW-501 hit — so `Spend.unpriced` counts it and the reason line says it is not counted. A catalog
  that rates nothing therefore under-reads the day's spend rather than pretending it is $0.00 free.
- **"No paid tier" means no paid tier in *scope*, not "no paid key".** `is_handback` tests
  `PAID_TIERS.isdisjoint(scope.tiers)`, so a run that would have used a paid model but had the tier
  withheld by the cap also triggers the handback — which is the useful reading of "the best available
  model is below the floor and no paid tier is in play".
- **One packet per session.** The advice reuses `latest_handoff_id(db, session)` before storing a new
  one, so a below-floor session does not accumulate a packet per answer; the line names the packet id
  it points at.
- **MCP has no header channel**, so the line goes into the outcome's notes there; `rules.advice: "off"`
  still suppresses it because the decision carries no advisory in that mode.

## Deviations

- **Vocabulary follows D19.** Every string this ticket adds qualifies the sense: `paid tier`,
  `paid-tier budget`, `paid-tier request(s)`, never "paid" bare, so a grep can tell the paid tier
  from a licensed feature. The refusal line and the `NoRouteError` message were renamed from
  "paid budget" to "paid-tier budget" for exactly that reason.
- **The packet's model/effort line and its "Run ruff, mypy, pytest" step are superseded** by this
  session's instructions: one verification pass, no mypy, no full suite; a targeted run instead.
- **The packet's central premise was wrong (P1).** `paid_scopes` was not "a feature waiting to be
  switched on" — it was an id with no package, so `enabled()` was always False and every scope
  already withheld paid tiers. The ticket therefore adds the package and the two plugin seams; it
  deliberately adds **no** new "is the feature installed" branch to core, and the two hand-registration
  helpers in `tests/router_support.py` / `tests/run_support.py` were the only places that had to
  change (one of them; the other still hand-registers, FU-502-5).
- **`confirm_above_usd` is not implemented here (P2)** because it already works.
- **Three of the packet's build items are deferred, not built:** `:floor` + quantization filter,
  `openrouter/auto`, and the battery/GPU-busy cloud suggestion (FU-502-1..3). Each is a candidate
  that needs either a catalog field or a virtual-model feature that does not exist; none of them is
  needed for the ticket's accept-when bar, and inventing a rate or a slug for them would violate D7.
- **`headwaters/core/engine.py`, `cli/runtime.py` and `daemon/service.py` needed no change.** The
  engine already registers `db`, `catalog` and `rules` as services (HDW-501 added exactly that), so
  the new plugins find everything they need on the registry the engine builds.
- **`tests/test_features_discovery.py::test_production_discovery_registers_no_example` was already
  failing** on arrival: it asserted `discover_features(reg) == []` while `ledger` and `tray` ship.
  It now asserts the named production packages. This is a one-line premise fix in a file this ticket
  touches anyway, and it keeps the "no example packages in production" intent while being true.
- **`tests/run_support.py` and `tests/test_gateway_chain.py` changed their premise:** the paid rig
  now turns the real feature on instead of faking a registration, and the star/non-star chain rigs
  state their flags explicitly rather than relying on the feature set being empty.
