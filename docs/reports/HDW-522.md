## Summary

`rules.yaml` accepts `keep_alive: "120"`, times it correctly with `parse_duration_s` (120 s) and
then sends it to Ollama as the quoted JSON string `"120"`, which Ollama rejects with HTTP 400
`time: missing unit in duration "120"`. The fix normalises once, at the config boundary: a bare
numeric `keep_alive` is stored as the same number of seconds as a Go duration (`"120"` -> `"120s"`),
so both wired paths - the keep-warm ping and the executor chat payload - carry a value Ollama takes.
Duration strings with a unit (and non-numeric text) keep their exact spelling, so no existing config
changes meaning.

The ticket's premise was half right and half wrong. A **quoted** numeric string was the defect, and
it is broader than reported: `"0"` and `"-1"` break every chat request the same way, while the
keep-warm tick skips them. A **bare YAML number** (`keep_alive: 120`) never reaches Ollama at all:
pydantic v2 does not coerce `int` to `str`, so the file is rejected at load (P2). That case is not a
400 source; it now fails with a message that names the form that works (`'120s'`) instead of
pydantic's "Input should be a valid string". Bare numbers were **not** added to the accepted
vocabulary.

## Files changed

- `headwaters/core/duration.py`: `normalize_keep_alive(text)` - a bare decimal (sign, integer or
  fraction, exponent form included) becomes `<seconds>s` (`"120"` -> `"120s"`, `"120.5"` ->
  `"120.5s"`, `"1e3"` -> `"1000s"`, `"-1"` -> `"-1s"`, `"0"` -> `"0s"`, surrounding whitespace
  dropped); anything else - `"30m"`, `"1h30m"`, `""`, `"abc"` - is returned unchanged. `Decimal`
  formats the number without an exponent so the result is always a Go duration literal. The module
  docstring now shows `120s` rather than the rejected `90`.
- `headwaters/core/rules.py`: `LocalTier.keep_alive` gained a description (it is now a `Field`) and
  two validators. `_keep_alive_is_text` (mode `before`) rejects a bare `int`/`float` with
  "write '120s' (or '30m'), not a bare number of seconds"; `_keep_alive_carries_a_unit` (mode
  `after`) applies `normalize_keep_alive`. The heartbeat validator's docstring notes that `-1` / `0`
  are stored as `-1s` / `0s` and still skip with `keep_alive_not_timed`.
- `catalog/rules.schema.json`: regenerated with `python -m headwaters.core.rules_io --write`; the
  only diff is the new `keep_alive` description (`tests/test_policy_order.py` asserts freshness).
- `docs/TROUBLESHOOTING.md`: the cold-load section now says to give `keep_alive` a unit and what
  happens to a quoted number and to a bare YAML number.
- `docs/ASSUMPTIONS.md`: `A-OLL-5` notes the client-side normalisation; a dated HDW-522 row records
  the rule, the forms and the one assumption left (the `-1s` / `0s` semantics).

## P1 - every code path that puts `keep_alive` on the wire

Grep over the repo (not the packet's list) finds exactly two senders, and both take the value from
`Rules.tiers.local.keep_alive`; there is no second config surface and no override:

| Path | Value | Wire type |
| --- | --- | --- |
| `headwaters/core/keepwarm.py:179` (`tick` -> `POST /api/chat`) | `local.keep_alive` as-is | quoted JSON string |
| `headwaters/core/executor/executor.py:247-248` -> `BackendRequest.keep_alive` (`types.py:83`, `str`) -> `headwaters/core/executor/ollama_convert.py:108` (`build_payload`) | `rules.tiers.local.keep_alive` as-is | quoted JSON string |

`headwaters/core/executor/ollama.py` only mentions `keep_alive` in its docstring; the cloud
(`litellm`) backend never receives it. `parse_duration_s` is the only reader that treats the value
as a number, and it is used for the interval and the heartbeat window, not for the wire.

## P2 - what parsing does

`Rules.model_validate({"tiers": {"local": {"keep_alive": v}}})`, probing pydantic 2.14 with the real
models:

| Written | Stored | `parse_duration_s` | On the wire before this ticket |
| --- | --- | --- | --- |
| `120` (bare YAML number) | **ValidationError** | - | never sent (rejected at load) |
| `120.0` | **ValidationError** | - | never sent |
| `true` | **ValidationError** | - | never sent |
| `"120"` | `"120"` | 120.0 | `"120"` - HTTP 400 |
| `"120s"` | `"120s"` | 120.0 | `"120s"` - accepted |
| `"30m"` / `"1h30m"` | unchanged | 1800.0 / 5400.0 | accepted |
| `"0"` / `"-1"` | `"0"` / `"-1"` | 0.0 / None | ping skipped; **chat 400** |
| `""` | `""` | None | ping skipped; chat sent `""` |
| `" 120 "` | `" 120 "` | 120.0 | `" 120 "` - HTTP 400 |

So `parse_duration_s("120")` is 120 s and `rules.py` happily times it, but the value that reached
Ollama was the quoted text. The defect is real for every quoted numeric form, not only `"120"`.

## Fix chosen and why

Normalise once, where the value is accepted (`LocalTier`), not where it is sent:

- one new pure helper in `duration.py`, next to `parse_duration_s`, with no import cycle
  (`rules` may not import `keepwarm`);
- both wired paths read `Rules.tiers.local.keep_alive`, so one validator fixes the ping **and** the
  chat payload, and no send site can drift from the other;
- duration strings are untouched byte for byte, so no existing `rules.yaml` changes meaning and
  `parse_duration_s` keeps returning the same seconds;
- the config vocabulary is not widened: a bare YAML number is still an error, it just says what to
  write.

Rejected alternatives: emitting an unquoted JSON number from both send sites (changes the payload
type, the `BackendRequest.keep_alive: str` contract and the pinned `"30m"` payload test, and splits
one rule across two files); normalising inside `build_payload`/`tick` (leaves the other path and
`interval_s` reading an un-normalised value); rejecting numeric strings at load (breaks working
configs for no reason - the value is unambiguous).

## Deviations

1. **The bare-number half of the ticket is not a 400 path.** `keep_alive: 120` is rejected by
   pydantic before any request. Rather than widening the vocabulary, the error message now names
   `'120s'`; the fix targets the quoted forms, which are the ones that reached Ollama.
2. **The defect is wider than `"120"`.** `"0"` and `"-1"` - both documented in `rules.py` as
   meaningful - were quoted the same way and broke every chat request; the normalisation covers them
   (`"0s"`, `"-1s"`).
3. **`catalog/rules.schema.json` regenerated** because the field gained a description; the diff is
   that one line.
4. **No new `docs/SDK_FACTS.md` row.** Nothing new was probed against Ollama: the 400 for a numeric
   string and the acceptance of a number were already verified rows from HDW-518, and the tests mock
   the transport. The one unverified point (`-1s` / `0s` sign semantics) is recorded as an
   assumption, not as a fact.
5. **FU-518-1 is closed by this ticket**; `docs/FOLLOWUPS.md` has no matching entry to update.
