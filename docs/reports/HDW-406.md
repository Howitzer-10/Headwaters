## Summary
Linux is the second packaging target and it is additive: the same payload layout as Windows, plus
one new entry point. `packaging/linux/install.sh` is generated by
`headwaters.packaging.linux.render_install_script()` (the committed file is compared byte for byte by
a test), copies the payload into `${HEADWATERS_ROOT:-${XDG_DATA_HOME:-$HOME/.local/share}/headwaters}`
and builds the private runtime with the bundled `uv` and `uv.lock`
(`uv sync --frozen --no-dev --python 3.11`), so no interpreter is bundled and no step needs root.
`headwaters/packaging/linux.py` then owns the systemd **user** unit at
`$XDG_CONFIG_HOME/systemd/user/headwaters.service`: `Type=simple`,
`ExecStart=<root>/runtime/.venv/bin/python -m headwaters.daemon`, `Restart=on-failure`,
`RestartSec=5`, `RestartPreventExitStatus=2 3`, `KillMode=mixed`, `TimeoutStopSec=30`,
`WantedBy=default.target`. Install is `daemon-reload` then `enable --now`, uninstall is
`disable --now`, `daemon-reload`, `reset-failed`, `--status` maps `is-enabled` to
enabled/disabled/absent/unknown, and `verify()` checks the runtime, both launchers and the unit after
the sync. Removal is split by owner exactly like HDW-405: the unit, the state tree and the keyring
entries belong to Python, the `runtime` tree belongs to the caller because the uninstaller executes
out of it, so `--uninstall` prints the `rm -rf` line instead of pretending to delete itself, and every
tree deletion is guarded by `is_inside` against the app root and the state dir. `build_linux` stages
`build/linux/itch` (`runtime/` plus `install.sh`) and prints `linux-beta`;
`packaging/butler/push_linux_beta.ps1` is a hand-run release step that nothing in `tests/`,
`.github/workflows` or pre-commit may call.

Because the session host is Windows and CI has no systemd, nothing here starts, stops or enables a
service. What *can* be proven is proven: the unit is asserted after parsing it, every side effect is
asserted under `tmp_path` through the injected `runner=`, and the exact `ExecStart` argv is started as
a real foreground daemon, watched through `/health` and stopped. The one bullet that needs a Linux
host is marked **NOT PROVEN** below, with the manual run written out in
`docs/RELEASE_CHECKLIST_LINUX.md`.

## Assumptions
- The row this ticket added to docs/ASSUMPTIONS.md is the authority for the design: one runtime
  layout for both targets, `install.sh` generated from Python and compared byte for byte, `uv sync`
  on the user's machine so no interpreter is bundled, a **user** unit rather than a system one,
  `python -m headwaters.daemon` rather than `headwaters start` as `ExecStart`, the restart policy with
  `2`/`3` prevented, removal split by owner, and the `ExecStart` argv proven by a real process.
- The six systemd facts (user unit path, `RestartPreventExitStatus`, one command per `ExecStart`,
  the XDG quoting/C-escape rules, `enable --now`, `loginctl enable-linger`) are recorded in
  docs/SDK_FACTS.md under "Linux packaging (HDW-406)" instead of being repeated here. They came from
  the official freedesktop manuals, not from SDK source, so the SDK-source read budget was untouched
  (0 of 5) and no bundled library version was bumped, which is why no existing SDK_FACTS row needed
  re-verification.
- **The daemon exit codes are the unit's restart policy.** `2` is an unreadable `rules.yaml` and `3`
  is another daemon holding the lock (both recorded by HDW-402's triage), so both are in
  `RestartPreventExitStatus`; `4` (no free port) is transient and is left to restart. If the daemon
  ever reports a *permanent* port failure with `4`, the unit would loop on it (FU-406-5).

## Deviations
- **Nothing was started, stopped or enabled, and the report says so.** The packet allows a
  "documented manual check" instead of the CI service smoke test, and that is the path taken: the
  unit is asserted as text and argv, the daemon argv is proven by a real process, and the service run
  is the owner's step in `docs/RELEASE_CHECKLIST_LINUX.md`. This is the ticket's one unproven item.
- **`ExecStart` uses the venv interpreter, and its path is quoted.** `_quote()` doubles backslashes
  and escapes double quotes the way `systemd.syntax` requires, which matters on a root with a space
  and makes the Windows-hosted test read the words back through a small `unescape()` helper rather
  than comparing raw text. On a real Linux install the words are unquoted because no path holds a
  space.
- **The daemon pid is compared with itself, not with the test's `Popen` pid.** On Windows a venv
  launcher hands off to another interpreter, so `process.pid` is not the daemon's pid; the test
  asserts causality instead (no daemon in an isolated home → this argv makes one appear and answer
  `/health` → stopping it makes it disappear). systemd on Linux does not care which pid a launcher
  picks for `Type=simple` either, so this is not a weakened assertion about the unit.
- **`build.payload_steps` gained an `uv_name` parameter and `runtime.missing_entries` an `entries`
  parameter** instead of a second copy of either. Both default to the Windows values, so
  `build_windows.py`, the Inno script and the existing tests are unchanged; the Linux target passes
  `"uv"` because the binary name differs and `uv.exe` would not execute on Linux.
- **`layout.Install`/`layout.installed_root()`/`layout.update_mode()` stay Windows-only.** Linux gets
  its own `LinuxInstall` rather than a generalised `Install`, so the HDW-405 windows installer,
  autostart XML and itch payload are untouched. The cost is that `headwaters doctor`'s `install`
  check still reads the Windows layout, so on Linux it reports a source checkout (FU-406-1).
- **No doctor check was added.** Whether the unit is enabled is a question only a systemd host can
  answer, so it is `linux.py --status` plus the release checklist rather than a `doctor` check that
  would have to shell out (FU-406-2). This is also why no positional test list needed the HDW-404 /
  HDW-403 treatment.
- **`docs/RELEASE_CHECKLIST.md` gained one pointer line and a new sibling file** rather than growing a
  Linux section: the Windows procedure is long and the packet explicitly forbids restyling it.

## Follow-ups
- FU-406-1 | packaging | `headwaters/packaging/layout.py` `installed_root()`/`update_mode()` |
  Both read only the Windows layout (`%LOCALAPPDATA%\Headwaters`, `.itch.toml`), so `headwaters
  doctor`'s `install` check reports a source checkout or "no update path" on a real Linux install.
  Teach them `LinuxInstall.default()` and the `XDG` roots, or have the check ask
  `headwaters.packaging.linux` when the platform is not Windows.
- FU-406-2 | doctor | `headwaters/control/doctor.py` | There is no check that the systemd user unit
  exists, is enabled and points at this install. It needs a child process (`systemctl --user
  is-enabled`, `show -p ExecStart`) the way the `--host` probe does, so the doctor never imports
  systemd-specific code, and it must degrade to `unknown` on a host without a user manager.
- FU-406-3 | release | `docs/RELEASE_CHECKLIST_LINUX.md` section 2 | The clean-Linux run has not
  happened: the unit is unproven against a real `systemd --user`. Every line of that section, plus
  the `systemctl --user status` and `loginctl`/logout lines, needs one pass on a fresh box; the
  report's NOT PROVEN bullet closes when that run is recorded in the release ticket.
- FU-406-4 | itch | `packaging/butler/push_linux_beta.ps1` | The `linux-beta` channel has not been
  created or pushed to, and the script is deliberately not wired into pytest or CI. Section 3 of the
  Linux checklist (`-Validate`, then the push) is the owner's step; the payload must be staged on
  Linux first, because `find_uv` would otherwise copy a Windows `uv.exe` under the name `uv`.
- FU-406-5 | packaging | `headwaters/packaging/linux.py` `PREVENT_RESTART_ON` | `Restart=on-failure`
  restarts the daemon on exit 4 (no free port). That is right for a transient clash and a tight loop
  if every port is permanently taken, so the pair needs an `StartLimitIntervalSec`/`StartLimitBurst`
  decision (or `4` added to the prevented codes once the daemon reports port exhaustion distinctly).
- FU-406-6 | packaging | `packaging/linux/install.sh` | A reinstall does `cp -R "$SOURCE"/. "$ROOT/runtime"/`,
  which merges and never deletes, so a module removed between versions stays behind. A staged copy
  plus an atomic swap (or `rsync --delete`) would make an upgrade exact; it was left out because it
  removes the ability to run the old runtime if the sync fails.
- FU-406-7 | itch | `packaging/linux/` | Linux ships no `.itch.toml`, because the itch app cannot
  register a systemd unit for the user; the store page has to say "unpack and run `./install.sh`" in
  those words. A future launcher could `xdg-open` the status page once a daemon exists.
- FU-406-8 | packaging | `headwaters/packaging/linux.py` `_install` | `systemctl --user` needs a user
  manager and a session bus; over a bare SSH connection without `loginctl`/`DBUS_SESSION_BUS_ADDRESS`
  the install fails after the sync and prints the linger hint. A headless path (`systemd-run --user`,
  or starting the daemon directly and leaving the unit for later) is not implemented.
