## Summary
The gateway now has the alias table v3 §5.1 asks for (`models.aliases` in `rules.yaml`) and one
resolver, `headwaters/gateway/aliases.py#requested`, that both faces call, so an IDE's own model
names mean the same thing on `/v1/chat/completions` and `/v1/messages`; this closes FU-301-2 and
the FU-302-1 duplication. An unmapped name stays an explicit request for that model and passes
through with failover, unless the request sends `x-headwaters-pin: true`, which now sets the new
`RouteRequest.pin_strict` and surfaces the provider's failure instead of cascading. Tool-schema
pass-through, the agentic `agentic_tools` floor, `BasicVerifier`'s tool-call schema check and the
`+verify`/`+quality` suffix syntax already existed from HDW-115/130/154/302, so this ticket pins
them with an end-to-end agent tool loop rather than rebuilding them.

  validation and `+verify`/`+quality`. All four already shipped (`gateway/openai_routes.py#_tools`,
  `core/policy`, `verify_basic.py#check_tool_calls`, `core/scope.py`). Rather than rebuild them this
  ticket adds the end-to-end tests the accept-when asks for and changes nothing that already
  worked; the alias table, the pin and explicit-model failover are new.
- `x-headwaters-pin` is the header the packet names, so it stays that; it is honoured only for an
  explicit model (or an alias that resolves to one). Sending it with `headwaters/auto` is ignored
  and recorded in the ASSUMPTIONS row -- a picker model has nothing to pin to.
- A strict pin still takes the in-place retry the wall allows (`_recover`'s `retry` action comes
  first), and only then becomes a hard failure instead of a cascade; "no failover" is read as no
  *model* failover, not as no retry.
- Two test-authoring fixes while iterating, not product changes: the tools fixture had a bare
  `yield` (ruff PT022) so it returns the rig, and three assertions first expected
  `ParsedModel.verify` to be `True`/the verify header to read `passed`; the code uses the string
  `"always"` and `pass`.
- `catalog/rules.schema.json` was regenerated mechanically and the default `rules.yaml` is
  unchanged (empty maps are omitted), so no shipped rule file changed.
