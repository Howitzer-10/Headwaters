## Summary

Provider registration is now catalog data. A `providers` array in the signed catalog (`ProviderEntry`
in `catalog/schema.py`, five rows in `catalog/seed_catalog.json`) is read through the new
`headwaters/core/providers.py` by the key store, `keys test`, model discovery (`provider:<name>`
sources) and `TargetBuilder` (route `openai/<model>` on the row's base URL), so `headwaters keys set
<name>` works for every row with no `rules.yaml` edit. Five providers were verified against their
own docs on 2026-11-03 and registered: nvidia (free_cloud), huggingface, mistral, pollinations
(all paid) and kilo (paid, keyless for its free models). The owner's naming directive is applied:
one canonical set of plain provider names, `KeyStore.providers()`, is the single source for the CLI
and the dashboard; no human-readable output names an environment variable; `keys set` normalises
`hf` and variable spellings to the provider and refuses an unknown name without `--provider`.

## Deviations

- Pollinations is paid and key-required: the packet's keyless premise is not in the provider's docs.
- Kilo is registered rather than deferred: it has a documented public API.
- The `rules.yaml` base-URL override named in the packet is not built (the base URL is signed catalog data; `openai_compatible` endpoints still work).
- Nvidia, kilo and pollinations have no key check (`keys test` reports unsupported), since no documented endpoint validates a key.
- A registered provider with no key sends a fixed placeholder key, so litellm's `openai/` route cannot fall back to the user's `OPENAI_API_KEY`.
- Keyless Kilo discovery runs on every refresh and a failure becomes a `kilo:` warning.
- Owner naming directive (user-directed, overrides the packet): see Summary. `KeyStore.save` stays permissive so existing store tests hold; the refusal lives in the CLI. `keys list` can never show the "No keys" hint because default rows always exist, so the hint is kept only for the empty case.
- The OpenCode key was not changed (deferred, A-OC-3).
