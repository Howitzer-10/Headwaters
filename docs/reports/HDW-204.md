## Summary
Added the first three front-door MCP tools to the shared daemon: `headwaters_do` (answer, diff or plan, with the checked unified diff, commands, model, tier, scope, `verified`, `relay`, `below_floor`, `suggestions` and a `headwaters://result/<id>` link), `headwaters_ask` (read-only Q&A over paths) and `headwaters_check` (verify a diff or code, no model call). Every tool has an `outputSchema`, structured content plus a short text rendering, and annotations. The shim now sends its working directory with each call (the workspace boundary, D9) and forwards resources, so the result link is readable through it. A below-floor local request shows `below_floor`, `suggestions` and the same warning as `headwaters pick` (FU-123-2).

## Deviations
- `async` is accepted as an argument but background jobs are HDW-206, so it runs now and adds a note. The Python parameter is `run_async` with an alias, because `async` is a keyword.
- The packet does not say how the shared daemon learns the project folder. D9 says the host shim passes it, so the shim sends its working directory in the request `_meta`. No rules key names a configured root (FU-203-2), so none is passed.
- The ticket's tool list says nothing about the shim, but `result_uri` is unreadable without resource forwarding (FU-202-2), so the shim now forwards resources. Prompts, progress and elicitation are still not forwarded.
- `headwaters_check` takes no `paths`: it checks the text you give it (and test-applies a diff in the workspace), not files.
- `run_blocking` moved from `link.py` to `headwaters/mcp/threads.py` so the tools reuse it. No behaviour change.
- No conflict with D7 to D14. D8 and D14 hold: the SDK is imported only inside `headwaters/mcp/`; the daemon imports no SDK or web framework.
