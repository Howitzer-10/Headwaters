## Summary

The keep-warm tick from HDW-201 already existed and already had the nine properties Part 1 §3 of the
packet claimed, so this ticket built no scheduler: the ping still rides
`Daemon._every(self.keep_warm_interval, self.keep_warm_once)`, unchanged and unconditional. What is
new is opt-in. `tiers.local.keep_warm_heartbeat: true` adds a literal interval
(`heartbeat_interval_s`), an idle backoff (`heartbeat_idle_backoff_s`) and an `expires_at` read from
`/api/ps` after a successful ping; with the flag off there is no interval override, no idle check, no
extra `/api/ps` read, and the tick is today's tick. `keep_warm_model`'s on-by-default behaviour is
untouched (§D3), `KeepWarm` still imports no router, quotas or ledger writer, and there is still one
POST per tick and no inner retry.

The one thing the probes changed: `keep_alive` is a Go duration string or a JSON number, and a bare
numeric **string** is a 400 — which our own parser accepts. Nothing in the packet depended on that,
so it is a follow-up, not a change here.

## Probe answers (P1–P6)

Ollama **was** installed and running: version `0.40.13` at `http://127.0.0.1:11434`, with
`qwen3.5:4b` (9.4 GB on the card). Every probe below was run live against it; probe scripts were
throwaway files outside the repo, the model was unloaded again at the end (`done_reason: "unload"`),
and no credential was involved.

- **P1 — does an empty-`messages` `/api/chat` with `keep_alive` (re)start the timer, and what does it
  return?** **Yes.** On a cold device the ping took **10 927.7 ms** and returned `done: true`,
  `done_reason: "load"`, `message.content: ""` — a load with nothing generated. `/api/ps`
  immediately after showed `expires_at` = ping time **+1800 s** for `"30m"`. A ping on a loaded
  model returns the same shape in tens of milliseconds. The existing tick's premise is real.
- **P2 — does `/api/ps` `expires_at` move forward after a ping?** **Yes, exactly.** Two pings 5 s
  apart: `expires_at` went `19:31:57 → 20:01:57` then `19:32:02 → 20:02:02` — the deadline moved
  forward by the 5 s between the pings, not by a fixed re-arm. So one ping per window keeps a model
  resident indefinitely, which is the whole premise of an interval knob, and the packet's acceptance
  item 2 is satisfied as written (no rewrite needed).
- **P3 — is `keep_alive` honoured as a string, or capped?** **Honoured, no cap observed.**
  `"30m"` → +1800 s, `"10m"` → +600 s, `"25s"` → +25 s; a JSON **number** `120` → +120 s. A numeric
  **string** `"120"` was **rejected**: HTTP 400 `{"error":"time: missing unit in duration \"120\""}`.
  That is a latent bug in our own `parse_duration_s` (it accepts a bare number) — a user who writes
  `keep_alive: "120"` passes validation and then every ping fails. Not fixed here (out of ticket:
  FU-518-1), and it is not what §D4 is about.
- **P4 — boundary thrash?** **A cliff, not a thrash, but the listing lags.** With a 15 s window the
  model was listed at 5 s and 10 s and gone at 15 s; a ping 12 s in (just under the window) re-armed
  in **8.6 ms** and pushed `expires_at` out by 25 s; a ping 5 s *past* the deadline still answered in
  **28.4 ms** because the server had not yet unloaded the model and `/api/ps` still listed it; a ping
  well past it (12 s window, ping at 22 s, model already gone from `/api/ps`) cost a **6107 ms**
  reload with `done_reason: "load"` — three orders of magnitude above the 8.6 ms re-arm. So the
  failure mode §D4's invariant exists to prevent is real (a cold weight reload), the transition is
  abrupt rather than oscillating, and `/api/ps` is not a reliable "expired" oracle — which is why
  `expires_at` is reported and never used as a control input.
- **P5 — is there a cheap, already-maintained timestamp of the last routed request?** **Yes, option
  (ii).** `decisions.ts REAL NOT NULL` with `CREATE INDEX idx_decisions_ts` is written for every
  routed request, and the daemon already owns `self.db`, so `SELECT MAX(ts)` is an indexed read with
  no new column, table or event. Slice 3 therefore reads the ledger rather than inventing a state
  path: `latest_decision_ts(db)` in `state_decisions.py`, injected into `KeepWarm` as a
  `Callable[[], float | None]`. Caveats recorded as deviations: it is *any* tier's request (the
  table stores the chosen model as JSON text, no tier column — deviation 2) and `None` (nothing ever
  routed) counts as idle.
- **P6 — cheap Windows idle/lock detection?** **Yes: `GetLastInputInfo` via `ctypes`, no
  dependency.** It returned the machine's idle time correctly and cost ≈0.6 µs per call, so it would
  be affordable once per tick. **Not implemented**: the packet only asks the question, and a
  heartbeat that backs off on OS idle rather than on our own traffic is a behaviour change nobody
  approved (FU-518-4). The heartbeat therefore backs off on routed traffic and on battery only.

## Deviations

1. **`parse_duration_s` moved from `keepwarm.py` to `headwaters/core/duration.py`** (packet says
   Slice 1 adds "no `keepwarm.py` change"). The §D4 validator lives in `rules.py`, which cannot import
   `keepwarm.py` (that is the wrong direction of the existing layer, and `keepwarm.py` already
   imports `rules.py`), so the parser had to be importable from `rules.py`. It moved verbatim;
   `keepwarm.py` re-exports it (`__all__` still lists it), so `tests/test_keepwarm.py` and any caller
   importing it from `keepwarm` are unchanged. `lint-imports` kept all 7 contracts without an
   `.importlinter` edit.
2. **The idle timestamp is *any* tier's newest routed request, not "no routed request has touched the
   local tier"** (§D5). `decisions` stores the chosen model inside `chosen` as JSON text — there is no
   tier column and no index that would answer "last *local* request" cheaply, so a local-only read
   would decode JSON per row. Reading `MAX(ts)` is one indexed row. The behavioural difference: a
   cloud request also counts as "somebody is at the machine", which is the same intent (do not warm a
   GPU nobody is using). FU-518-2 if strict local-only is wanted.
3. **`describe()` lives in `keepwarm.py`, the transition log in `service.py`** (§D8). The log line
   could not live in `KeepWarm`: `keep_warm_once` constructs a fresh `KeepWarm` on every tick, so an
   instance field for "previous state" would be reset each time and log every tick. The daemon owns
   `last_keep_warm` already, so it compares there and formats with `keepwarm.describe`, which keeps
   D18's "one source, three readers" intact. The vocabulary added is exactly the packet's
   (`resident`/`until=`, `idle backoff`, `paused (…)`), and no new reason string was invented except
   `idle_backoff`, which the packet names.
4. **`expires_at` is only read when the flag is on.** The packet puts `until=<expires_at>` inside the
   heartbeat mode (D8) and this ticket's "off is today, tick for tick" rule is stronger than a nicer
   status line: with the flag off there is no second `/api/ps` read, so `KeepWarmResult.expires_at` is
   `None` and the CLI prints the old line. The field exists in the status dict in both modes (`None`
   when off) so the shape does not change with the flag.
5. **`test_heartbeat_does_not_resurrect` asserts today's tick returns, not `skipped: disabled`.** The
   packet's test 15 expects `skipped: disabled` after flipping the flag, but with `keep_warm_model`
   still `auto` (the default) turning the *heartbeat* off resumes the *existing* tick, which pings —
   `disabled` belongs to `keep_warm_model: off`, not to this flag. The test was written to the D3
   truth: after the flip, `pinged`, `expires_at is None`, and no extra `/api/ps` read, i.e. exactly
   the pre-HDW-518 behaviour.
6. **The shutdown test touches two private members and shortens the wait.**
   `test_heartbeat_stops_on_shutdown` sets `daemon._stop = asyncio.Event()` (what `serve` installs
   before it creates the tasks) and runs `_every(lambda: 0.01, daemon.keep_warm_once)` rather than
   `daemon.keep_warm_interval`, because the real interval is 900 s and the test must not idle 15
   minutes for the second tick. It also reads `KeepWarm._last_request` to prove the daemon wired the
   ledger timestamp rather than a new state path. The loop, the task body and the stop event are the
   real ones; only the sleep is shortened.
7. **`catalog/rules.schema.json` regenerated** (not named by the packet). `tests/test_rules.py`
   asserts the committed schema equals `Rules.model_json_schema()`, so the three new keys had to be
   written by `python -m headwaters.core.rules_io --write`. This was the one genuine failure the
   verification pass found, and it was fixed rather than the test.
8. **P4's premise needs a footnote rather than a rewrite.** The packet treats "just under the window"
   vs "just over" as a clean pair; the probe showed `/api/ps` keeps listing an expired model for a few
   seconds and a ping in that gap still answered cheaply (28.4 ms), with the 6107 ms reload only once
   the model was really gone. The §D4 invariant is still right; the *observable* cliff is softer than
   the packet implies, and `expires_at` is therefore reported, never trusted as a control input.
9. **Nothing was added to `docs/DECISIONS.md`.** D3 and D4 already say what this ticket needed; no new
   decision was required, and none was written.
