## Summary

The tray is a fourth surface over the same daemon, not a fourth opinion. It speaks only the daemon
internal API: `GET /v1/status` (extended with a `tray` block), the new `GET /v1/keys` and the new
`POST /v1/scope`, which is `rules_edit.set_setting` followed by the same reload-and-report path as
`POST /v1/reload` — so the tray, `headwaters scope`, the MCP tool and the dashboard cannot disagree
about what "scope is local" means. Scope and Private Mode come from the daemon at startup, never
from a file of the tray's own; a missing daemon is a normal state (red icon, most items disabled),
never a dialog. Provider names are the registry's, verbatim, through `KeyStore.providers()`: no
label table, no display-name map, no rewriting, and no provider-name string literal in the tray
module. `pystray` and `Pillow` are the only new dependencies, and every icon is drawn at runtime
with `PIL.ImageDraw`, so there is no asset to package.

Two things are worth the reader's attention. First, **the tests found two real defects in the menu
code**, both pystray behaviours that no amount of reading had surfaced (below). Second, **the
packet's first accept-when — "the Windows manual checklist passes" — is not met**: no real
notification area, logon task or toast was ever exercised on this machine. Everything a headless
run can prove was proven; the manual items are listed one by one, UNVERIFIED, with the substitute
check named.

## Two defects the tests caught

Both were in the pystray-facing code and neither was visible by reading the packet:

1. **Every action raised `ValueError`.** The first binding wrapper was
   `lambda _icon, _item, call=action: call()`. pystray decides whether an action fits by reading
   `co_argcount`, which counts a keyword parameter that has a default, so that wrapper looked like a
   three-argument action and was rejected at `MenuItem` construction. Fixed by `_bind(action)`, a
   real two-parameter closure. The fact is now in `docs/SDK_FACTS.md`.
2. **The "Scope" and "Keys" labels disappeared.** A nested `pystray.Menu` was being passed where an
   item belongs; pystray wants the submenu as the *item's action*
   (`MenuItem("Scope", Menu(...))`), and a bare `Menu` in the item list loses the parent label (and
   `len(Menu)` raises, because `Menu` is not a tuple). Fixed in `build_menu`, which now recurses into
   an item that owns a child menu.

The tests were written first and failed on both, which is why the `builder`/`menuitem`/`menu`
injection seams exist at all (deviation 9).

- One row added to `docs/ASSUMPTIONS.md` (2026-11-12, "The tray app (HDW-504, D18)"): the tray is a
  surface over the daemon's API, `effective_scope` is `local` when Private Mode *or* Airplane is on
  while the Scope radio shows the stored `default_scope`, provider names are the registry's verbatim,
  the label vocabulary is `set`/`not set`, the colour rules, the Windows-only spawn and the
  flag-controlled single scheduled task.
- Six rows added to `docs/SDK_FACTS.md` under "Tray icon library (HDW-504)" (pystray 0.19.5, Pillow
  13.0.0): the `(icon, item)` action contract, the `co_argcount` rejection of a defaulted third
  parameter, submenus as an item whose action is a `Menu` (and `Menu` not being a tuple),
  `Menu.SEPARATOR` with no `MenuItem.SEPARATOR`, no `pystray.__version__`, and `ImageDraw` +
  `getpixel` giving a plain 4-tuple.
- No external service was contacted and no provider API was called. `uv lock` resolved from the
  existing lockfile and the local cache only.

## Deviations

1. **`POST /v1/scope` takes `{"key": ..., "value": ...}`, not `{"scope": ...}`.** The packet names the
   path and needs one path for both scope and Private Mode ("Same internal API path as scope"), and
   `rules_edit.set_setting` already speaks key/value for exactly `EDITABLE_KEYS`
   (`default_scope`, `private_lock`, `strategy`). Reusing it means a key no surface may edit from here
   is a **400 with a reason**, and `strategy` works without a second endpoint.
2. **The two endpoints answer in an envelope with `ok`.** `/v1/keys` answers
   `{"ok": true, "providers": [...]}` and `/v1/scope` answers
   `{"ok", "key", "value", "previous", "default_scope", "private_lock", "airplane", "applied"}`
   (`+ "reason"` when not applied). The packet constrains the **provider objects** (`provider`,
   `alias`, `source` only, no `env_var`) and that is what the test pins; the envelope matches the
   rest of the internal API (`/v1/reload`).
3. **`Daemon.start_tray()` refuses to spawn when `PYTEST_CURRENT_TEST` is set.** The repo's live
   tests start real daemons and `tests/live_support.py` only sweeps `headwaters.daemon` and
   `headwaters.mcp` markers, so a real tray child would leak out of the suite as an orphan GUI
   process. Consequence, stated plainly: no test proves a real spawn; the flag gate and the
   never-raise contract are tested with an injected launcher instead (FU-504-1).
4. **The tray survives the daemon stopping.** The daemon does not terminate its child on shutdown.
   Deliberate: the tray's own *Restart daemon* stops the daemon, so terminate-on-shutdown would kill
   the process that asked for the restart. A red icon plus *Restart daemon* is the useful state, and
   `InstanceLock(state/tray.lock)` keeps it to one icon, so a later `headwaters start` (or
   `headwaters tray`) does not stack a second. The cost is that `headwaters stop` leaves a red icon
   (FU-504-4).
5. **The daemon-side spawn is Windows-only** (`os.name != "nt"` → no tray from the daemon).
   `pystray`'s notification-area backend here is the Windows one, which is what this ticket targets;
   `headwaters tray` itself is not refused on other platforms, where pystray would try its xorg
   backend (FU-504-5).
6. **Any `last_status` other than `ok` is red, not only an error.** `outcomes.status` is the word the
   router records for the last routed request; `verify_failed` means the request did not end well, so
   the icon says so. The packet says "the last request failed" and this is that sentence read
   literally.
7. **The Scope radio checks the stored `default_scope`, while the status line shows
   `effective_scope`.** A lock does not rewrite the setting it overrides (v3.3 §C's intersection), so
   a person with Private Mode on sees `Local · Private Mode` above a radio still on `auto`. That is
   the honest pair: the stored choice, and what is actually in force. The tray never writes the
   scope from the effective value.
8. **The tray feature flag defaults on** (`DEFAULT = True`), so a `rules.yaml` with no `features:`
   block starts the tray with the daemon, as the packet's "starts with the daemon" requires. Two
   off-switches the packet did not ask for exist: `HEADWATERS_NO_TRAY` in the tray's own process, and
   the pytest guard of deviation 3.
9. **Injection seams beyond the packet's two.** The packet names the icon object and
   `opener(url) -> bool`; `TrayApp` also takes `notifier`, `doctor`, `restarter`, `client`, `interval`
   and `builder`. `builder` is not cosmetic: it is how the tests exercise the real `build_menu`
   against a fake `MenuItem`/`Menu` without importing pystray, after the two defects above.
10. **No explicit toast rate limiter.** The packet's build bullet mentions "rate-limited toasts on
    tier switches". Nothing on the 2 s refresh path ever notifies — only a person's own action does —
    so a storm is not reachable today and a limiter would be dead code. If a background source ever
    notifies, it needs one (FU-504-3).
11. **`tray_status()` catches an exception from `KeyStore.entries()`** and reports `keys_set = 0`
    instead of failing `/v1/status`. Not in the packet; a locked or broken credential store must not
    take out the status read for every surface (proven by
    `test_a_broken_credential_store_does_not_break_the_status_read`).
12. **The menu's keyless provider reads `ollama — not set`.** D18 and the packet allow exactly one
    suffix and no third word, and `ollama` needs no key, so the label is truthful but arguably
    ambiguous. Changing the vocabulary is an owner decision, not a tray decision (FU-504-6).
