## Summary
Added the shared daemon: `headwaters start|stop|daemon-status`, one process that owns the router, catalog refresh and keep-warm, with a token-authenticated internal JSON API and a streamable-HTTP MCP endpoint on one loopback port. Ports are picked around the Hyper-V/WSL excluded ranges and written to a state file. The package-boundary question from FU-124-1 / FU-TRI-3 is settled as D14: `gateway` owns the HTTP server, `mcp` owns the SDK, and a new `daemon` package is the composition root. This is also the first production wiring of `Router`, so it closes recheck R3 (remote-model patterns reach every executor).

## Deviations
- Package boundary changed, as the packet asked (FU-124-1): D14. The packet layout put the daemon under `headwaters/mcp/`; it is in `headwaters/daemon/`, with the HTTP server in `headwaters/gateway/`. `uvicorn` was added to the web-framework contract.
- The ticket says "`headwaters daemon` process". There is no such CLI command: `python -m headwaters.daemon` is the process and `headwaters start` launches it. A `headwaters daemon` command would have to import the server code, putting the web stack into the CLI, which the new contracts forbid.
- Added `headwaters daemon-status` (not in the ticket): without it `start` and `stop` give no way to see the chosen ports. Small and read-only.
- The internal API and the MCP endpoint share one port (default 4002). The gateway and dashboard ports are also probed and recorded in the state file, but nothing binds them in this ticket.
- Background tasks use daemon threads instead of `asyncio.to_thread`. A real `headwaters stop` hung because `asyncio.run` joins the default executor; details are in the assumptions row.
- No conflicts with D7 to D13 found. D7 is why the HTTP server sits in the gateway package; D8 (SDK imports only in `headwaters/mcp/`) holds; D13 is why the engine passes the remote patterns (tested).
