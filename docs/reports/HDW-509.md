## Probes

### P1 — isolation evidence

`lint-imports.exe` (console script; `python -m lint_imports` fails with "no module") reports
literally: **"Contracts: 7 kept, 0 broken"** over 323 files / 2131 dependencies. The 7 contracts:

1. `core-is-a-leaf` — `headwaters.core` must not import `headwaters.features`, `.gateway`, `.mcp`, `.daemon`, `.control`, `.installer`, `.packaging`, or `.cli`.
2. `litellm-only-in-cloud-executor` — only `headwaters.core.executor.cloud` may import `litellm`; the allowed edge is via `importlib` (invisible to the linter) and is enforced by `tests/test_litellm_guard.py` instead (`unmatched_ignore_imports_alerting = none`).
3. `mcp-sdk-only-in-mcp` — only `headwaters.mcp` may import the `mcp` SDK.
4. `web-framework-only-in-gateway` — only `headwaters.gateway` may import `fastapi`, `starlette`, `uvicorn`.
5. `daemon-is-a-root` — nothing may import `headwaters.daemon` (composition root, D14).
6. `daemon-no-direct-mcp-sdk` — `headwaters.daemon` may not import `mcp` directly (`allow_indirect_imports = True`).
7. `daemon-no-direct-web-framework` — `headwaters.daemon` may not import `fastapi`/`starlette`/`uvicorn` directly.

**Does this cover the ★ claim? Only partly.** The ★ claim is "core never imports
`headwaters.features.*`", and only `core-is-a-leaf` enforces it — statically. What could break the
isolation and still pass all 7 contracts: (a) a dynamic import (`importlib` / `__import__`) from
`headwaters.core` into a feature module — the linter is blind to it, by its own admission for the
litellm case; (b) string-based feature loading that resolves to a feature module without a static
import edge; (c) the reverse edge `features → core` is allowed by design and unguarded (correct, but
not the claim). The claim holds for static imports today; the dynamic-import gap is a residual risk,
not a current defect.
