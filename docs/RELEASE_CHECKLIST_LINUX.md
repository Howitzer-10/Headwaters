# Linux release checklist

Use this for every Linux release. It covers the per-user prefix, `install.sh`, the systemd **user**
unit and the itch.io `linux-beta` channel. Everything here is per user: no step needs `sudo`, and
nothing is written outside `$XDG_DATA_HOME` and `$XDG_CONFIG_HOME` (HDW-406).

Two facts this document depends on and that a test asserts:

- the payload ships no interpreter: `install.sh` runs `uv sync --frozen --no-dev --python 3.11`
  against the bundled `runtime/uv` and `runtime/uv.lock` on the user's machine;
- the app root is `$XDG_DATA_HOME/headwaters` (default `~/.local/share/headwaters`, override with
  `HEADWATERS_ROOT`) and holds `runtime/`, while the unit is
  `$XDG_CONFIG_HOME/systemd/user/headwaters.service` (default `~/.config/systemd/user/`). The state
  (database, log, `daemon.json`) stays where `headwaters.core.paths.state_dir()` puts it, so
  `HEADWATERS_HOME` still wins for a test or a portable install.

## 0. What the owner has to supply once

| What | Where it goes | Notes |
| --- | --- | --- |
| a Linux x86_64/arm64 build host | — | the `uv` binary is platform-specific, so the shipping payload is staged on Linux |
| `uv` on the build host | `HEADWATERS_UV` (default: `uv` on `PATH`) | copied into `runtime/uv`; no Python is bundled |
| butler | `brew`/`curl -LsSf https://astral.sh/uv/install.sh`… then `butler login` | only for the itch upload |

A payload staged on Windows is **not shippable**: `build_linux` says so, because `find_uv` would
copy `uv.exe` under the name `uv` and the file would not execute on Linux.

## 1. Build

```bash
uv run python scripts/build_linux.py            # or: uv run python -m headwaters.packaging.build --target linux
```

It stages `build/linux/payload` (`pyproject.toml`, `uv.lock`, `uv`, `headwaters/`, `catalog/`),
fails if any of those is missing, then stages `build/linux/itch` (`runtime/` plus the generated
`install.sh`) and prints the channel it is meant for. `--dry-run` prints the plan and writes
nothing. There is no compiler and nothing is signed on this target.

`packaging/linux/install.sh` is generated by `headwaters.packaging.linux.render_install_script()`;
`tests/test_packaging_linux.py` compares the committed file with the generator, so edit the
generator and regenerate rather than editing the script.

## 2. Clean Linux run (manual, IT MUST BE RUN BY A PERSON)

The HDW-406 session ran on Windows, where systemd cannot start, so this section is **unproven**: it
is written from the code and from the tests that read the unit text and run the daemon argv, not
from an actual install. Do it on a fresh Linux box (or a container with a real user session) and
tick every line.

- [ ] `uv` is on `PATH` for the user doing the install; nothing else is preinstalled.
- [ ] `tar xf headwaters-linux-beta.tar.gz -C ~/hw-payload && cd ~/hw-payload && ./install.sh`.
- [ ] No `sudo` prompt appears and nothing is written to `/usr`, `/etc` or `/opt`.
- [ ] `~/.local/share/headwaters/runtime/.venv/bin/headwaters` and `headwaters-mcp` exist, and
      `uv.lock` and `pyproject.toml` are in `runtime/`.
- [ ] `~/.config/systemd/user/headwaters.service` exists and `systemctl --user cat headwaters.service`
      prints exactly that file.
- [ ] `systemctl --user is-enabled headwaters.service` prints `enabled` (the unit is
      `WantedBy=default.target`).
- [ ] `systemctl --user status headwaters.service` shows the service **active (running)** and the
      daemon answers on loopback: `headwaters status` and the dashboard URL both work.
- [ ] Log out and back in: the service is active again with no terminal left open.
- [ ] Log out with `loginctl enable-linger` **unset**: the service stops, which is what the install
      script's last hint warns about. `loginctl enable-linger "$USER"` makes it survive.
- [ ] Kill the daemon (`systemctl --user kill -s KILL headwaters.service`): systemd restarts it
      after ~5 s (`Restart=on-failure`, `RestartSec=5`).
- [ ] Make the daemon exit 2 (point `rules.yaml` at an unreadable file) and restart: systemd does
      **not** loop — `RestartPreventExitStatus=2 3` holds it, and `systemctl --user status` shows
      `code=exited, status=2`. Same for exit 3 (another daemon holds the lock). Exit 4 (no free
      port) does restart, which is intended.
- [ ] `systemctl --user stop headwaters.service` stops it and `kill -TERM` reaches the daemon
      (`TimeoutStopSec=30`, `KillMode=mixed`).
- [ ] `headwaters doctor` reports the `install` check as OK and names the update path.
- [ ] Reinstall over itself (`./install.sh` again): no error, database and rules preserved.
- [ ] Uninstall, keeping state:
      `~/.local/share/headwaters/runtime/.venv/bin/python -m headwaters.packaging.linux --uninstall --yes`.
      The unit file is gone, `systemctl --user is-enabled` says `not-found`, the service is
      stopped, and the database is still there. The runtime is **not** deleted (the process runs
      out of it) — the command prints the `rm -rf` line to run afterwards.
- [ ] Uninstall again with `--remove-state --remove-keys`: settings, history and the saved keys in
      the login keyring are gone.
- [ ] Nothing is left in `~/.config/systemd/user/`, and `~/.local/share/headwaters` disappears once
      the printed `rm -rf` has been run.

Record the result (distribution and version, date, build hash, anything that failed) in the release
ticket.

## 3. itch.io `linux-beta` channel

```powershell
.\packaging\butler\push_linux_beta.ps1 -User howitzer-10 -Game headwaters -Validate
```

The script refuses to run unless `build\linux\itch` holds `install.sh`, `runtime\uv`,
`runtime\uv.lock` and `runtime\pyproject.toml`, and the channel is fixed at `linux-beta`
(`build.CHANNEL_LINUX`) so a Windows and a Linux upload can never land on the same channel.
`-Validate` runs `butler validate` first. Like the Windows script it is deliberately **not** wired
into pytest, pre-commit or CI: an upload is a release decision, and no test may reach the network.

Linux has no `.itch.toml`: the itch app cannot install or launch a systemd unit for the user, so a
Linux download is a tarball the user unpacks and runs `./install.sh` from. The store page must say
so in the same words, or a user will look for a launcher that is not there.

## 4. After the release

- [ ] `git log --oneline -1` matches the build you uploaded.
- [ ] Keep the staged payload hash; the build host's `uv` version is part of what shipped.
- [ ] If the clean-Linux run found a problem, file it before the next release and note it here.
